2. 왜 파이썬 파일이 6개 필요한가▲ 맨 위

4파트가 해야 하는 일

4파트(대응·리포트)는 2파트가 준 탐지 결과를 받아서 끝까지 처리해야 한다. 이 일은 한 덩어리가 아니라 서로 다른 6가지 일이다. 일 하나에 파이썬 파일 하나를 만든다.

  • 일 1. 이벤트가 얼마나 위험한지 보고 처리 방식(등급)을 정한다 → 1번 classifier.py
  • 일 2. 이벤트 상태를 적고, 1·3파트가 실행할 조치 요청을 만들고, 결과가 오면 상태를 바꾼다 → 2번 playbook.py
  • 일 3. 탐지가 틀렸을 때(오탐) 조치를 되돌리고 기록을 남긴다 → 3번 false_positive.py
  • 일 4. 이벤트별 처리 기록(티켓)을 만들고, 결과가 오면 갱신하고, 담당자 알림을 요청한다 → 4번 ticket.py
  • 일 5. 초동 대응 리포트를 만든다 → 5번 report.py
  • 일 6. 위 5가지를 순서대로 이어 붙여 한 번에 돌린다 → 6번 main.py

일마다, 그 일이 없으면 생기는 문제

  • 일 1이 없으면 모든 이벤트를 똑같이 처리해야 한다. 전부 자동으로 막으면 위험하고, 전부 사람이 보면 느리다.
  • 일 2가 없으면 등급만 있고 실제 조치는 아무것도 실행되지 않는다. 조치를 실행하는 1·3파트는 "무엇을, 누구에게"를 받아야 움직인다.
  • 일 3이 없으면 정상 사용자가 잘못 막힌 채로 남고, 탐지 규칙을 고칠 자료도 없다.
  • 일 4가 없으면 승인을 기다리는 이벤트와 처리 중인 이벤트를 담당자가 추적할 수 없다. 담당자에게 알리는 요청도 만들 곳이 없다.
  • 일 5가 없으면 어떤 조치를 했고 결과가 어땠는지 사람이 읽을 기록이 남지 않는다.
  • 일 6이 없으면 파일이 각각 따로 있을 뿐, 이벤트 파일을 넣어 끝까지 처리하는 입구가 없다.

왜 한 파일로 만들지 않고 6개로 나눴나

  • 한 파일에 다 넣으면 길어져서 에러가 났을 때 어디가 틀렸는지 찾기 어렵다. 파일마다 한 가지 일만 하면 그 파일만 열어 보면 된다.
  • 파일마다 따로 실행해서 확인할 수 있다. 1번이 맞는지 확인한 뒤에 2번을 만들 수 있다.
  • 앞 파일의 결과가 뒷 파일의 재료가 된다. 1번의 등급이 2번의 재료, 2번의 조치 요청이 3번과 4번의 재료다. 그래서 1번부터 순서대로 만든다.
  • 기준이 바뀌면 그 일을 맡은 파일만 고친다. 예를 들어 등급 기준(점수)이 바뀌면 classifier.py만 고친다.
  • 팀원이 필요한 파일만 가져가 쓸 수 있다. 예를 들어 오탐 처리만 필요하면 false_positive.py만 쓰면 된다.

이 "왜"는 대영이 처음에 준 파일 순서와 각 파일의 역할로 Claude가 풀어 쓴 것이다. 팀에서 정한 이유가 따로 있으면 그 문장을 고친다.

  • 6번 main.py : 1차 완료 (2026-10-27). 파일 읽기, 이벤트별 조치 요청과 티켓, 조치 결과 반영, 리포트 저장, 5-2단계 오탐 처리(오탐 입력 파일을 읽어 복구 요청과 오탐 기록)까지 이어 붙였다. 알림 요청 줄은 아직 없다.

이어 붙여 본 것: main.py로 1~5번을 이어 붙여 샘플 이벤트 7건을 실행했다. 티켓 6장, 리포트 파일 6개가 생겼다. (main_example.py는 1~4번만 이어 붙인 예시 파일이다.)

4. 데이터가 흐르는 길▲ 맨 위

detections.json (2파트가 만든 탐지 이벤트, 공통로그 2번)
   ↓ 1번 classifier.py     이벤트의 점수로 등급 글자를 정한다
   ↓ 2번 playbook.py       상태를 적고 조치 요청 6칸을 만든다 (공통로그 3번)
   ↓ 4번 ticket.py         조치 요청이 있으면 티켓을 만든다 (make_ticket)
   ↓
1파트(계정·세션) / 3파트(IP 차단)가 조치를 실행하고 결과를 돌려준다 (공통로그 5번)
   ↓ 2번 apply_result      결과를 보고 상태를 바꾼다
   ↓ 4번 update_ticket     같은 결과로 티켓을 갱신한다
   ↓ 4번 make_alert_request 담당자 알림 요청을 만든다 (공통로그 4번, 1파트가 읽는다)
   ↓ 5번 report.py         조치 이력(containment_log.json, 공통로그 6번)과 티켓으로 초동 대응 리포트를 만든다
오탐이면 → 3번 false_positive.py   복구 요청 + 오탐 기록 (공통로그 7번)
6번 main.py 가 위 전부를 순서대로 이어 붙인다 (지금은 오탐과 알림 요청 줄이 빠진 1차)
순서 주의 : 2번 apply_result, 4번 update_ticket 은 5번 make_report 보다 먼저 부른다.

이 흐름은 파일 사이의 약속이다. 누가 알림 함수를 부를지는 팀이 정해야 한다. (공통로그 4번 그림에 "누가 이 함수를 부르지는 팀이 정해야 해요"라고 적혀 있다.)

5. 파일 6개 소개▲ 맨 위

1번 classifier.py (완료)

  • 소개 : 이벤트 1건의 위험 점수를 보고 대응 등급 글자 하나를 정하는 파일이다.
  • 왜 필요한가 : 모든 이벤트를 똑같이 자동으로 막으면 위험하고, 전부 사람이 보면 느리다. 점수에 따라 처리 방식을 나누는 기준이 필요하다.
  • 기능 : 점수 80 이상은 "즉시 자동조치", 50 이상은 "승인 후 조치", 나머지는 "모니터링만". 단, 점수가 높아도 VIP 계정·IP면 "승인 후 조치"로 낮춘다.
  • 받는 것 : 이벤트의 user, src_ip, risk_score, rule, VIP 명단
  • 내보내는 것 : 등급 글자 하나
  • 함수 : check_vip, event_check
  • 다른 파일과의 관계 : 2번이 가져다 쓴다.

2번 playbook.py (완료)

  • 소개 : 등급을 받아 이벤트 상태를 적고, 1·3파트가 실행할 조치 요청을 만드는 파일이다.
  • 왜 필요한가 : 등급만으로는 아무것도 실행되지 않는다. 실행하는 쪽은 "무슨 조치(action), 누구에게(target)"를 알아야 한다. 또 이벤트가 지금 어느 단계인지 추적해야 한다.
  • 기능 : 이벤트 유형에 맞는 조치 이름과 대상을 정한다. 등급에 따라 처음 상태(조치중, 승인대기, 모니터링)를 적는다. 조치 요청 6칸(공통로그 3번)을 만든다. 조치 결과(공통로그 5번)를 받으면 상태를 완료·실패 등으로 바꾼다.
  • 받는 것 : 이벤트 1건, VIP 명단, 상태 서랍장, 조치 결과
  • 내보내는 것 : 조치 요청 6칸 또는 None
  • 함수 : choose_action, choose_target, make_request, first_status, apply_result, run_playbook
  • 다른 파일과의 관계 : 1번을 가져다 쓴다. 만든 조치 요청은 1·3파트와 3번, 4번이 쓴다.

3번 false_positive.py (완료)

  • 소개 : 탐지가 틀렸다(오탐)고 확인되었을 때 복구하고 기록하는 파일이다.
  • 왜 필요한가 : 정상 사용자를 잘못 막았으면 바로 풀어 줘야 한다. 또 "이상이라고 했지만 정상이었던 사례"를 남겨야 탐지 규칙을 개선할 수 있다.
  • 기능 : IP 차단이면 차단 해제, 계정 잠금이면 잠금 해제 요청을 만든다. 조치가 실패했거나 연습 실행이었거나 되돌릴 수 없는 조치(접속 종료)면 복구 요청은 만들지 않는다. 오탐 기록(공통로그 7번)은 항상 false_positive_feedback.json에 쌓는다.
  • 받는 것 : 이벤트, 원래 조치 요청, 원래 조치 결과, 오탐 이유, 확인한 사람
  • 내보내는 것 : 복구 요청 6칸 또는 None, false_positive_feedback.json
  • 함수 : choose_restore_action, make_restore_request, make_feedback, save_feedback, handle_false_positive
  • 다른 파일과의 관계 : 2번이 만든 조치 요청과 1·3파트의 조치 결과를 받아서 쓴다.

4번 ticket.py (완료)

  • 소개 : 조치가 필요한 이벤트마다 티켓을 만들고, 결과가 오면 티켓을 갱신하고, 담당자 알림 요청을 만드는 파일이다.
  • 왜 필요한가 : 승인 대기 중인 이벤트나 처리 중인 이벤트를 담당자가 한눈에 추적하려면 이벤트별 처리 기록 단위가 필요하다. 5번 리포트도 티켓을 재료로 쓴다.
  • 기능 : 티켓 1장 만들기(이벤트 11칸 + 조치 요청 5칸 + 상태·결과·시각), 조치 결과로 티켓 상태 바꾸기, 알림 요청 4칸(공통로그 4번) 만들기.
  • 받는 것 : 이벤트, 조치 요청, 상태 글자, 조치 결과, 알림 단계와 알림 글자
  • 내보내는 것 : 티켓 서랍장, 알림 요청 4칸
  • 함수 : make_ticket, update_ticket, make_alert_request
  • 다른 파일과의 관계 : 2번의 조치 요청과 상태를 받는다. 티켓은 5번이 읽는다. 알림 요청은 1파트가 읽는다.

5번 report.py (후속 조치만 남음)

  • 소개 : 초동 대응 리포트를 만드는 파일이다.
  • 왜 필요한가 : 이벤트에 어떤 조치를 했고 결과가 어땠는지 사람이 읽을 수 있는 한 장의 기록으로 남기기 위해서다.
  • 기능(계획) : 리포트 5부분(사고 개요, 탐지 근거, 조치 내역, 현재 상태, 후속 조치)을 만든다. 조치 내역은 containment_log.json(공통로그 6번)에서 읽는다.
  • 지금 완료한 것 : read_log(filename) (조치 이력 파일 읽기), make_report(ticket, logs) (사고 개요, 탐지 근거, 조치 내역, 현재 상태. 후속 조치는 팀 기준을 기다린다), save_report(lines, filename) (줄 목록을 json 파일로 저장)
  • 함수 : read_log, make_report, save_report (저장은 json.dump, 파일 이름 끝은 .json)
  • 다른 파일과의 관계 : 4번의 티켓을 받고, 1·3파트가 만든 조치 이력 파일을 읽는다.

6번 main.py (1차 완료)

  • 소개 : 1~5번을 순서대로 이어 붙이는 파일이다.
  • 왜 필요한가 : 지금까지는 파일마다 따로 만들었다. 실제로 쓰려면 이벤트 파일을 읽어 끝까지 한 번에 돌리는 입구가 필요하다.
  • 기능 (5단계, 함수 없이 위에서 아래로 한 번 돈다) : 1 파일 3개 읽기 → 2 빈 서랍장 statuses, tickets 만들기 → 3 이벤트마다 run_playbook, 조치 요청이 있으면 make_ticket → 4 조치 결과로 apply_result, update_ticket → 5 티켓마다 make_report, save_report. 확인 코드는 if __name__ == "__main__": 안에 있다.
  • 받는 것 : detections.json, vip_accounts.json, containment_log.json
  • 내보내는 것 : 티켓이 있는 이벤트마다 report_EVT-001.json 같은 파일 1개
  • 지금 없는 것 : handle_false_positive 줄(오탐 신호를 어떻게 받을지 미정), make_alert_request 줄(누가 부를지 팀 미정). 4단계의 조치 결과는 가짜 값이다. 진짜는 1·3파트가 돌려준 값을 넣는다.
  • 가장 중요한 것은 순서다. 4단계(결과 반영)가 5단계(리포트 저장)보다 먼저여야 저장된 리포트에 조치 결과:success, 현재 상태:완료가 적힌다. 순서가 바뀌면 에러 없이 결과 없음, 조치중이 저장된다.

6. 팀 표준 글자▲ 맨 위

띄어쓰기까지 똑같이 써야 한다.

  • 등급 : 즉시 자동조치 / 승인 후 조치 / 모니터링만
  • 상태 : 신규 / 승인대기 / 조치중 / 완료 / 실패 / 모니터링
  • 조치 결과 : success / fail / skipped / approval_required
  • 조치와 실행 파트 : lock_account, unlock_account, terminate_session은 1파트, block_ip, unblock_ip는 3파트
  • 이벤트 유형 : ABNORMAL_LOGIN, OFFHOUR_LOGIN, UNAUTHORIZED_ACCESS, MALICIOUS_IP, TRAFFIC_SPIKE, CORRELATED_ATTACK

공통로그 7번 그림 예시에는 suspicious_login이라는 유형이 나온다. 위 6개에 없다. 이 글자가 이벤트로 들어오면 2번 run_playbook이 요청을 만들지 않고 상태를 신규로 둔다.

7. 공통로그 칸▲ 맨 위

이름표는 팀이 정한 표준이다. 바꾸면 다른 파트가 못 읽는다.

  • 1번 접속 로그 access.log (1·3파트 → 2파트) : time, user, role, src_ip, target, action(login, admin_login, view_payments, download_payments, view_users, refund, grant_item, deactivate, access_denied), detail, result(success/fail), source. 4파트는 직접 읽지 않는다. (2026-10-26에 카드를 다시 보고 고쳤다. 이전 문서에는 timestamp, dst_ip, resource, reason으로 잘못 적혀 있었다.)
  • 2번 탐지 결과 detections.json (2파트 → 4파트) : event_id, detected_at, rule, event_type, user, src_ip, risk_score, priority(HIGH/MEDIUM/LOW), asset, impact_scope, evidence. 주의 : evidence는 글자가 아니라 시각 글자들의 목록이다.
  • 3번 조치 요청 (4파트 → 1·3파트) : event_id, action, target, response_level, reason, dry_run
  • 4번 알림 요청 (4파트 → 1파트) : event_id, level, to, message
  • 5번 조치 결과 (1·3파트 → 4파트) : event_id, action, target, result, message, timestamp, dry_run
  • 6번 조치 이력 containment_log.json (1·3파트 → 4파트) : timestamp, event_id, action, target, reason, result, dry_run
  • 7번 오탐 처리 기록 false_positive_feedback.json (4파트 → 2파트) : event_id, username, event_type, detected_as_anomaly, risk_score, is_actual_anomaly, false_positive_reason, confirmed_by, recorded_at
  • 8번 테스트 시나리오 결과 test_result.md (전원, 합친 뒤에 채운다) : tc_id, scenario, expected, actual, pass

4파트 해야 할 일 6개 (조건 그림): 대응 등급 분류, 플레이북·이벤트 상태 관리, 승인 게이트(자동·승인·보류), 오탐 대응(복구·기록), 티켓 생성·상태 갱신, 초동 대응 리포트 생성. 이 중 "보류"는 팀 표준 등급 3개에 없다. 대응 방법은 팀원용 문서의 "등급에 보류 같은 새 글자가 생기면" 칸에 있다.
