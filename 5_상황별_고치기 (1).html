0. 이 문서 쓰는 법▲ 맨 위

다른 파트와 합치다가 "이름이 다르다", "모양이 다르다", "글자가 다르다"가 나오면 이 문서를 연다.

상황마다 이렇게 적었다.

  • 어느 파일의 어느 함수를 고치나
  • 코드 창에서 Ctrl+F로 찾을 글자
  • 무엇으로 바꾸나 (바꾸기 전과 후)
  • 왜 이렇게 고치나
  • 고친 뒤 확인하는 방법

5분 안에 고칠 수 있게 줄 번호가 아니라 함수 이름과 찾을 글자로 적었다. 줄 번호는 코드를 고치면 바뀌기 때문이다.

  • 규칙이 다를 때 : 6. 규칙이 다를 때 ↗
  • 한글이 깨질 때 : 7. 한글이 깨질 때 ↗

이 문서는 지금 있는 코드 기준이다. 파일이 늘면 이 문서에도 같은 칸을 더한다.

1. json 파일 이름과 하는 일▲ 맨 위

다른 사람이 "그 파일은 이런 일을 하는 파일이에요"라고 말해도 알아듣게 적었다.

이름이 같아도, 이름이 달라도 아래 설명으로 같은 파일인지 확인한다.

detections.json (탐지 결과 파일)

  • 하는 일 : 2파트(탐지)가 "이상한 일이 있었다"고 적어 두는 파일이다. 이벤트 한 건이 한 칸이다.
  • 누가 만드나 : 2파트
  • 누가 읽나 : 4파트의 6번 main.py가 읽어서 이벤트를 하나씩 run_playbook에 넣는다.
  • 안에 든 것 : 이벤트 목록. 한 건에 event_id, detected_at, rule, event_type, user, src_ip, risk_score, priority, asset, impact_scope, evidence (공통로그 2번)
  • 다른 이름으로 불릴 때 : "탐지 결과", "이벤트 파일", "alerts", "events"
  • 우리 코드에서 이름이 적힌 곳 : classifier.py 맨 아래 테스트, main_example.py 맨 위

vip_accounts.json (VIP 명단 파일)

  • 하는 일 : 함부로 자동으로 막으면 안 되는 중요한 계정과 IP의 명단이다.
  • 누가 만드나 : 4파트가 임시로 만든 샘플. 진짜 명단은 팀이 정한다. (팀이 정해야 함)
  • 누가 읽나 : classifier.py의 check_vip가 이 명단을 보고 VIP인지 정한다.
  • 안에 든 것 : {"vip_users": [계정들], "vip_ips": [IP들]}
  • 다른 이름으로 불릴 때 : "VIP 목록", "중요 계정 목록", "예외 명단"
  • 우리 코드에서 이름이 적힌 곳 : classifier.py 맨 아래 테스트, main_example.py 맨 위

containment_log.json (조치 이력 파일)

  • 하는 일 : 1·3파트가 조치를 실행할 때마다 한 건씩 적어 두는 기록장이다.
  • 누가 만드나 : 1·3파트 (공통로그 6번)
  • 누가 읽나 : report.py의 read_log가 읽어서 리포트의 "조치 내역"에 쓴다.
  • 안에 든 것 : timestamp, event_id, action, target, reason, result, dry_run
  • 다른 이름으로 불릴 때 : "조치 로그", "대응 이력", "action_log"
  • 우리 코드에서 이름이 적힌 곳 : report.py 맨 아래 테스트. 6번 main.py에서도 read_log에 넣어 준다.
  • [확인 필요] 기록 여러 건이 [ {...}, {...} ] 목록으로 든 파일인지 팀에 물어봐야 한다.

false_positive_feedback.json (오탐 기록 파일)

  • 하는 일 : "탐지는 이상하다고 했지만 사실은 정상이었다"는 기록을 쌓아 두는 파일이다. 2파트가 탐지 정확도를 고치는 데 쓴다.
  • 누가 만드나 : 4파트의 false_positive.py의 save_feedback
  • 누가 읽나 : 2파트 (공통로그 7번)
  • 안에 든 것 : 기록 목록. 한 건에 event_id, username, event_type, detected_as_anomaly, risk_score, is_actual_anomaly, false_positive_reason, confirmed_by, recorded_at
  • 다른 이름으로 불릴 때 : "오탐 로그", "피드백 파일"
  • 우리 코드에서 이름이 적힌 곳 : false_positive.py의 handle_false_positive 한 곳

access.log (접속 로그)

  • 하는 일 : 1·3파트가 로그인과 접근을 한 줄씩 적는 기록이다. 2파트가 이것을 보고 탐지한다.
  • 4파트는 이 파일을 읽지 않는다. 우리 코드에 이름이 없다.

리포트 파일 (6번 main.py가 만든다)

  • 5번 save_report가 만드는 파일이다. 이름은 6번 main.py의 5단계가 save_report(lines, "report_" + event_id + ".json")로 넣어 준다. 티켓이 있는 이벤트마다 1개씩 생긴다. 우리가 정한 모양은 report_ + 이벤트번호 + .json (예: report_EVT-001.json). 안은 줄 글자들의 목록이다. 다른 사람이 글 파일(.txt)을 원하면 save_report 안의 json.dump(...) 줄을 for line in lines: 와 file.write(line + "\n") 2줄로 바꾼다. Ctrl+F로 json.dump(lines를 찾는다.

test_result.md (테스트 결과)

  • 하는 일 : 전원이 합친 뒤에 테스트 결과(tc_id, scenario, expected, actual, pass)를 채우는 표다. 4파트 코드는 이 파일을 만들지 않는다.

2. 파일 이름이 다를 때▲ 맨 위

상황 : 다른 파트가 "우리 파일은 alerts.json이에요"처럼 이름이 다르다.

고치는 방법은 하나다. 글자로 적힌 파일 이름만 바꾼다. 코드의 나머지는 건드리지 않는다.

detections.json 이름이 다를 때

  • 고칠 곳 : classifier.py 맨 아래 테스트 with open("detections.json" ..., 그리고 6번 main.py
  • 찾을 글자 : detections.json
  • 바꾸는 법 : 따옴표 안의 글자만 새 이름으로 바꾼다.
바꾸기 전 : with open("detections.json", "r", encoding="utf-8") as file:
바꾼 뒤   : with open("alerts.json", "r", encoding="utf-8") as file:
  • 왜 : classifier.py의 함수들은 파일을 읽지 않고, 이벤트 값만 받는다. 파일을 여는 줄은 테스트에만 있다.
  • 확인 : 해당 파일을 직접 실행해서 EVT-001 즉시 자동조치 같은 줄이 나오면 된다.

vip_accounts.json 이름이 다를 때

  • 고칠 곳 : classifier.py 맨 아래 테스트, main.py
  • 찾을 글자 : vip_accounts.json
  • 바꾸는 법 : 위와 같이 따옴표 안의 글자만 바꾼다.

containment_log.json 이름이 다를 때

  • 고칠 곳 : report.py 맨 아래 테스트 read_log("containment_log.json"), main.py
  • 찾을 글자 : containment_log.json
  • 바꾸는 법
바꾸기 전 : logs = read_log("containment_log.json")
바꾼 뒤   : logs = read_log("action_log.json")
  • 왜 : read_log 함수 안에는 파일 이름이 없다. 부르는 쪽이 이름을 넣어 준다. 그래서 부르는 줄만 고치면 된다.

false_positive_feedback.json 이름이 다를 때

  • 고칠 곳 : false_positive.py의 handle_false_positive 함수 안
  • 찾을 글자 : false_positive_feedback.json (파일 안에 2곳 : handle_false_positive와 맨 아래 테스트)
  • 바꾸는 법 : 두 곳 다 같은 새 이름으로 바꾼다.
바꾸기 전 : save_feedback(feedback, "false_positive_feedback.json")
바꾼 뒤   : save_feedback(feedback, "fp_feedback.json")
  • 왜 : 맨 아래 테스트가 같은 파일을 읽어서 건수를 센다. 한 곳만 바꾸면 테스트가 없는 파일을 읽다가 에러가 난다.
  • 확인 : 파일을 실행해서 맨 아래 숫자(기록 건수)가 나오면 된다.

3. 파일 안 모양이 다를 때▲ 맨 위

이름은 같은데 안의 모양이 다른 경우다. 에러 글자로 구분한다.

detections.json 이 목록이 아니라 {"events": [...]} 처럼 감싸져 있을 때

  • 증상 : for event in detections:에서 이벤트 대신 events 같은 글자가 나오고, event["user"]에서 TypeError: string indices must be integers
  • 고칠 곳 : detections = json.load(file) 줄을 쓰는 곳 (classifier.py 테스트, main.py)
  • 바꾸는 법
바꾸기 전 : detections = json.load(file)
바꾼 뒤   : detections = json.load(file)["events"]
  • 왜 : ["events"]로 감싸진 바깥을 한 겹 벗겨서 안의 목록만 꺼낸다. 이름은 실제 파일의 이름표로 쓴다.

containment_log.json 이 목록이 아니라 기록 한 건({...})일 때

  • 증상 : report.py에서 TypeError: string indices must be integers가 log["event_id"]에서 난다. for log in logs가 기록 한 건의 이름표("timestamp" 등)를 하나씩 꺼내기 때문이다.
  • 고칠 곳 : report.py의 read_log 함수. return (logs) 바로 위
  • 바꾸는 법
    if isinstance(logs, dict):     # logs가 한 건(서랍장)이면
        logs = [logs]              # 한 건짜리 목록으로 감싼다
    return (logs)
  • 왜 : make_report의 for는 목록을 기대한다. 한 건이어도 목록으로 만들어 주면 make_report는 그대로 쓴다.
  • 확인 : report.py를 실행해서 이력 3줄이 나오는지 본다.

containment_log.json 이 줄마다 한 건씩 적힌 파일(JSON Lines)일 때

  • 증상 : json.load에서 json.decoder.JSONDecodeError: Extra data
  • 고칠 곳 : read_log 함수의 with 안 두 줄
  • 바꾸는 법
바꾸기 전 :     logs = json.load(file)
바꾼 뒤   :     logs = [json.loads(line) for line in file if line.strip()]
  • 왜 : 이 파일은 줄마다 JSON 한 건이다. 줄을 하나씩 읽어 json.loads로 바꾸고 목록으로 모은다. 빈 줄은 건너뛴다.

false_positive_feedback.json 을 2파트가 "목록이 아니라 한 건씩 줄로" 원할 때

  • 고칠 곳 : false_positive.py의 save_feedback 함수
  • 바꾸는 법 : 팀이 모양을 정한 뒤에 같이 정한다. 지금은 [ {...}, {...} ] 목록으로 쌓는다. (팀이 정해야 함)

vip_accounts.json 의 이름표가 다를 때

  • 증상 : KeyError: 'vip_users'
  • 고칠 곳 : classifier.py의 check_vip 함수
  • 찾을 글자 : vip_users, vip_ips
  • 바꾸는 법 : 두 곳의 ["vip_users"], ["vip_ips"] 따옴표 안 글자를 실제 파일의 이름표로 바꾼다.

evidence 가 목록이 아니라 글자일 때

  • 증상 : 근거: 줄이 로, 그, 인, ...처럼 글자마다 쉼표가 들어간다.
  • 고칠 곳 : report.py의 make_report 함수
  • 찾을 글자 : ", ".join(
  • 바꾸는 법
바꾸기 전 : lines.append("근거:" + ", ".join(ticket["event"]["evidence"]))
바꾼 뒤   : lines.append("근거:" + ticket["event"]["evidence"])
  • 왜 : 글자는 join이 필요 없다. 카드 2번은 목록이라고 되어 있으니 목록이면 그대로 둔다.

4. 칸 이름이 다를 때▲ 맨 위

상황 : 다른 파트가 user 대신 username, src_ip 대신 source_ip처럼 다른 이름을 쓴다.

증상 : KeyError: '이름'. 에러 글자 안의 이름이 우리 코드가 찾는 이름이다.

고치는 방법 (모든 칸 이름 공통)

  • 1 에러 글자에서 이름을 읽는다. 예 KeyError: 'user'
  • 2 코드 창에서 Ctrl+F로 ["user"]를 찾는다. 따옴표와 대괄호까지 같이 검색한다.
  • 3 아래 목록에서 해당 이름이 쓰인 파일과 함수를 확인하고, 그 곳만 새 이름으로 바꾼다.
  • 4 실행해서 에러가 사라지는지 본다.

바꾸면 안 되는 곳 : 서랍장을 새로 만드는 줄의 왼쪽 이름표("user": event["user"]의 왼쪽)는 다른 파트가 읽는 이름일 수 있다. 오른쪽 event["..."]가 받아 오는 곳이다. 먼저 어느 쪽 이름이 틀렸는지 확인하고 바꾼다.

6. 규칙이 다를 때▲ 맨 위

점수 기준(80, 50)이 다를 때

  • 고칠 곳 : classifier.py의 event_check
  • 찾을 글자 : >= 80(2곳), >= 50(1곳)
  • 바꾸는 법 : 숫자를 새 기준으로 바꾼다. 80이 2곳이다. 첫째는 점수 판정, 둘째는 "80점 이상이고 VIP면" 검사다.
  • 왜 : 둘이 같은 기준이어야 한다. 한 곳만 바꾸면 VIP 검사가 엉뚱한 점수에서 실행된다.

VIP 규칙이 다를 때

  • 고칠 곳 : classifier.py의 check_vip (VIP인지), event_check 끝(VIP면 어떤 등급으로 낮추나)
  • 찾을 글자 : check_vip, "승인 후 조치"

이벤트 유형 → 조치 짝이 다를 때

  • 고칠 곳 : playbook.py의 choose_action
  • 찾을 글자 : 유형 글자(예 OFFHOUR_LOGIN)
  • 바꾸는 법 : 해당 if/elif의 유형 목록을 바꾼다. 새 유형은 in [...] 목록에 더한다.
  • 대상(target)이 바뀌면 choose_target도 같이 본다. IP를 막으면 src_ip, 계정에 하면 user다.
  • 조치를 되돌리는 짝이 바뀌면 false_positive.py의 choose_restore_action도 같이 고친다.

모르는 이벤트 유형이 들어올 때

  • 증상 : 조치 요청이 안 나오고 상태가 신규로 남는다. 에러는 없다.
  • 고칠 곳 : 유형이 정말 새로 생긴 거라면 choose_action에 더한다.

새 등급(예 보류)을 더할 때

  • 고칠 곳 3곳 : classifier.py의 event_check(새 등급을 돌려줄 조건), playbook.py의 first_status(새 등급의 처음 상태), playbook.py의 run_playbook(새 등급일 때 요청을 만들지)
  • 안 고쳐도 되는 곳 : ticket.py
  • 안 고치면 : first_status의 마지막 else로 가서 상태가 신규가 된다.

조치가 성공하면 티켓을 바로 완료로 두지 않고 싶을 때

  • 배경 : 강의에서는 "조치 성공"과 "사고 처리 완료"를 다른 일로 본다. (팀이 정해야 함)
  • 고칠 곳 : ticket.py의 update_ticket
  • 찾을 글자 : "success"
  • 바꾸는 법 : success일 때 상태를 "완료" 대신 다른 글자(예 "조치중")로 둔다.
  • 같이 볼 곳 : playbook.py의 apply_result도 같은 규칙이다. 두 곳이 어긋나면 이벤트 상태와 티켓 상태가 달라진다.

연습 실행(dry_run)을 쓰고 싶을 때

  • 고칠 곳 : playbook.py의 run_playbook
  • 찾을 글자 : make_request(event, level, False)
  • 바꾸는 법 : False를 True로 바꾼다. 또는 run_playbook에 dry_run을 받는 칸을 더하고 main.py가 정해서 넘긴다.

알림을 누가 부를지 정해졌을 때

  • 고칠 곳 : main.py. ticket.py의 make_alert_request는 그대로 쓴다.
  • 방법 : 부를 조건이 생기면 make_alert_request(event, level, message)를 불러서 돌려준 서랍장을 1파트에 넘긴다.

후속 조치 문장

  • 고칠 곳 : report.py의 make_report 맨 아래 "후속 조치" 부분 (아직 안 썼다)
  • 팀 기준이 정해지면 그 문장을 status별 if / elif로 쓴다.

7. 한글이 깨질 때▲ 맨 위

  • 증상 : UnicodeDecodeError: 'cp949' codec can't decode byte ...
  • 원인 : 윈도우는 파일을 열 때 기본으로 cp949 방식으로 읽는다. 팀 json 파일은 한글이 utf-8로 저장되어 있다.
  • 고칠 곳 : 파일을 여는 줄 전부. Ctrl+F로 open(을 찾는다.
  • 바꾸는 법
바꾸기 전 : with open(filename, "r") as file:
바꾼 뒤   : with open(filename, "r", encoding="utf-8") as file:
  • 써 넣는 곳("w")도 같다. 쓰는 방식과 읽는 방식이 같아야 한다.
  • 우리 코드에서 open(이 있는 곳 : classifier.py 맨 아래 테스트(2곳), false_positive.py의 save_feedback(읽기, 쓰기)와 맨 아래 테스트, report.py의 read_log, main_example.py 맨 위
  • 주의 : 예전에 encoding 없이 만든 false_positive_feedback.json이 폴더에 있으면 읽다가 에러가 난다. 그 파일을 지우고 다시 실행한다. 기록 안의 한글이 깨진 채 남아 있기 때문이다.
  • 여기서 한 줄 더 : json.dump의 ensure_ascii=False는 한글을 \uXXXX로 바꾸지 않고 그대로 적는 옵션이다.

8. 합칠 때 5분 순서▲ 맨 위

9. main.py에서 막힐 때▲ 맨 위

6번 main.py를 돌릴 때 실제로 난 일과 날 수 있는 일이다. 코드 창에서 Ctrl+F로 찾을 글자를 검색한다.

  • 지금 4단계의 result는 EVT-001 하나만 있는 가짜 값이다. 1·3파트가 결과를 목록으로 돌려주면 이렇게 쓴다. (results가 결과 서랍장들의 목록이라고 가정한 예시다. 목록 이름과 모양은 팀이 정한 뒤 맞춘다.)

리포트 파일 이름을 바꾸고 싶을 때

  • 주의 : + event_id +는 지우지 않는다. 지우면 모든 이벤트가 같은 파일에 덮어쓰인다.
  • 글 파일(.txt)을 원하면 이 문서 1장 "리포트 파일"의 방법대로 save_report 안을 고친다.

main.py를 다른 파일에서 import 하면 리포트 파일이 만들어진다

  • 원인 : 1~5단계가 if __name__ == "__main__": 밖(맨 왼쪽)에 있다. import 하면 위에서 아래로 전부 실행된다.
  • 지금은 main.py가 맨 끝 입구라서 다른 파일이 import 하지 않는다. 그래서 그대로 둔다.
  • 나중에 다른 파일이 import 해야 하면 1~5단계를 def main(): 안으로 넣고 if __name__ == "__main__": 아래에서 main()을 부른다. (이 변경은 대영이 정한다)

오탐 처리(5-2단계)에서 막힐 때

아래는 실제로 난 일과 날 수 있는 일이다. 코드 창에서 Ctrl+F로 찾을 글자를 검색한다.

  • events 칸 수 0이 나온다 (에러는 없다) : event[event_id] = event처럼 events에서 s가 빠졌다. 서랍장 이름 events가 왼쪽, 이벤트 1건 event가 오른쪽이다. 찾을 글자 : event[event_id]
  • KeyError: 'event_id' (오탐 줄에서) : events["event_id"]처럼 따옴표를 붙였다. 변수 event_id를 쓸 때는 따옴표를 뗀다. → events[event_id], requests[event_id]
  • NameError: name 'reason' is not defined : item[reason]처럼 따옴표를 뗐다. 칸 이름 글자는 따옴표를 붙인다. → item["reason"], item["confirmed_by"]
  • NameError: name 'file' is not defined : 파일을 읽는 줄에 file(...)이라고 썼다. → read_false_positive_input("false_positive_input.json")
  • ImportError: cannot import name 'read_false_positive_input' : false_positive.py에 함수 6이 없다. 파일 맨 아래 테스트 블록 위에 함수 6을 쓴다.
  • 복구 요청: None : 에러가 아니다. 조치 결과가 success가 아니거나, 원래 조치가 terminate_session이거나, dry_run이 True이면 복구할 게 없어 None이다. 오탐 기록은 그래도 저장된다.
  • KeyError: 'EVT-004' 같은 이벤트 번호 : 오탐 입력 파일에 적은 이벤트에 티켓이 없다(모니터링만이라 requests, events에 칸이 없다). 입력 파일의 event_id를 티켓이 있는 이벤트로 바꾼다.
  • 복구 요청 줄이 아예 안 나온다 : false_positive_input.json이 같은 폴더에 없거나 []이다. 이 파일이 없으면 read_false_positive_input이 []을 돌려줘서 for가 한 번도 안 돈다.
  • UnicodeDecodeError : false_positive_input.json을 UTF-8로 저장했는지 본다. 예전에 encoding 없이 만든 false_positive_feedback.json이 있으면 지우고 다시 실행한다.

10. 후속 조치 규칙이 다를 때▲ 맨 위

report.py의 make_report 맨 아래(return (lines) 바로 위)에 후속 조치 주석 틀이 있다. 지금은 주석이라 돌지 않는다. 4줄 규칙(승인대기, 실패, 완료, 그 외)은 Claude가 만든 임시 규칙이고 팀이 확정한 것이 아니다.

문장만 바뀔 때

  • 따옴표 안 글자만 고친다. 예: "후속 조치:보안 담당자 승인 필요" → 팀이 정한 문장.
  • 쓰려면 주석 틀 8줄의 맨 앞 # 를 지운다. 칸 수는 if가 4칸(현재 상태 줄과 같은 칸), lines.append가 8칸이다.
  • 쓰면 줄 수가 19 → 20, 경우 3은 16 → 17이 된다. 테스트 파일의 기대 숫자 주석도 같이 고친다.
  • 확인 : python report.py에서 줄 수 20, 20, 17, 내용이 같은가: True. main.py에서 저장 내용 같은가: True.

상태가 늘 때

  • 팀 표준 상태 글자는 신규, 승인대기, 조치중, 완료, 실패, 모니터링이다. 새 상태 글자는 ticket["status"]에 들어오는 글자와 똑같이 쓴다.
  • elif 2줄을 else: 줄 바로 위에 더한다.
elif ticket["status"] == "모니터링":
    lines.append("후속 조치:경과 관찰")
  • else는 맨 마지막에 한 번만 둔다. else 아래에 elif를 쓰면 SyntaxError가 난다.

LLM으로 바뀔 때

  • 팀이 후속 조치를 LLM으로 쓰기로 하면 주석 틀 8줄을 지우고 한 줄로 바꾼다.
lines.append("후속 조치:" + make_follow_up(ticket))
  • make_follow_up은 예시 이름이고 아직 없는 함수다. 새로 만들어야 한다. 이 함수가 ticket을 받아 글자 하나를 돌려줘야 한다. None을 돌려주면 "글자" + None이라 TypeError가 난다.
  • 강의에서는 LLM이 사고 개요와 후속 조치 문단만 쓰고, 근거는 원본 데이터다. 없었던 조치나 안 된 승인을 지어내면 안 된다. 함수에 넘기는 값은 티켓의 값만 쓴다.
  • LLM 호출은 줄 수가 달라질 수 있다(여러 줄이면 append를 줄마다 쓴다). 줄 수 확인 숫자는 그때 다시 정한다.
