1. 코드를 어떻게 생각해서 쓰나▲ 맨 위

처음 보는 문제도 아래 6단계를 종이에 적고 나서 코드를 쓴다. 모든 파일을 이 순서로 만들었다.

6단계

  • 1단계 : 입력과 출력을 적는다. 무엇이 들어오고 무엇이 나가야 하나. 예시 한 건씩 눈으로 본다.
  • 2단계 : 출력 칸마다 "이 값이 입력 어디에 있나?"를 묻는다.
  • 3단계 : 규칙을 한글 문장으로 먼저 적는다. 코드가 아니라 말로.
  • 4단계 : 일을 한 가지씩 나눠 함수 이름을 붙인다. 한 함수는 한 가지 일만 한다.
  • 5단계 : 함수 하나를 쓰면 바로 실행해서 확인한다. 전부 쓰고 한 번에 돌리지 않는다.
  • 6단계 : 마지막에 함수들을 이어 붙인다. 이어 붙이는 함수는 다른 함수를 부르기만 한다.

값이 어디서 오나 (제일 중요한 질문)

코드에 쓰는 모든 이름은 아래 4곳 중 하나에서 와야 한다. 4곳 다 아니면 에러다.

  • 곳 1 : def 괄호 안에 있는 이름. 이 함수를 부르는 쪽이 값을 넣어 준다.
  • 곳 2 : 위쪽에 이름 = ...으로 만든 이름. (같은 함수 안, 또는 파일 맨 위)
  • 곳 3 : 서랍장에서 꺼낸 값. event["user"]처럼 이름표로 연다.
  • 곳 4 : 다른 파일에서 import 해 온 이름.

쓰다가 "이게 어디서 왔지?" 하고 막히면 이 4곳을 순서대로 찾는다. 찾으면 그 줄을 따라 쓰고, 못 찾으면 만들어야 하는 값이다.

테스트 코드에 쓰는 값도 같다. test_event의 칸 이름은 공통로그 2번 카드에서, 값은 그림 예시나 "내가 정한 테스트 값"에서 온다. 어디서 왔는지 주석에 적어 둔다.

말 → 코드 (문제 문장에 왼쪽 말이 보이면 오른쪽 코드 모양을 떠올린다)

  • "A면 X, B면 Y, 아니면 Z" → if / elif / else
  • "A, B, C 중 하나면" → if 값 in ["A", "B", "C"]
  • "A 이상이면" → >=
  • "A이고 B이면" → 조건1 and 조건2
  • "같지 않으면" → !=
  • "같으면" → == (= 하나는 "담는다"이다)
  • "이름표로 값을 찾는다" → 서랍장["이름표"]
  • "request의 action 칸" → request["action"] (한국어 "의"가 [ ]가 된다)
  • "결과를 이름에 담는다" → 이름 = 값 (오른쪽을 먼저 계산해서 왼쪽 이름에 넣는다)
  • "함수를 부른다" → 함수이름( 값 ) (넣는 순서는 그 함수의 def 줄 괄호 순서)
  • "기록해 둔다 / 상태를 바꾼다" → 서랍장[칸] = 값 (return 없음)
  • "계산해서 알려 준다" → return 값
  • "해당 없음" → return None
  • "먼저 기본값을 정하고 예외면 고친다" → level = ...로 먼저 적고 마지막에 return level
  • "파일에서 읽는다" → with open(...) as file: + json.load(file)
  • "파일에 적는다" → with open(..., "w") as file: + json.dump(...)
  • "지금 시각" → datetime.now().strftime("%Y-%m-%d %H:%M:%S")
  • "이 파일을 직접 실행할 때만" → if __name__ == "__main__":

코딩할 때 늘 하는 생각

  • 큰 문제는 작게 쪼갠다. 한 함수에서 두 가지 일을 하려고 하면 쪼갠다.
  • 함수는 "받는 것 → 돌려주는 것" 두 줄로 먼저 적는다. 이 두 줄이 안 적히면 아직 이해 못 한 것이다.
  • 다른 함수를 부를 때는 그 함수의 def 줄을 열어서 칸 개수와 순서를 맞춘다.
  • 따옴표를 볼 때마다 묻는다. 글자 그대로인가, 변수인가? 따옴표가 있으면 글자, 없으면 변수다.
  • 값을 돌려주는 것(return)과 서랍장을 바꾸는 것(서랍장[칸] = 값)을 구분한다.
  • 쓰고 나면 실제 값 하나로 한 줄씩 따라가 본다. "맞겠지"로 넘기지 않는다.
  • 에러가 나면 맨 아래 줄부터 읽는다. 맨 아래가 무엇이 틀렸는지, 그 위가 어느 줄인지 알려 준다.
  • 들여쓰기는 칸 수를 센다. def가 0칸이면 그 안은 4칸, if 안은 8칸이다. 눈으로 맞추지 않는다.

막혔을 때 묻는 질문 5개

  • 이 줄은 무엇을 받아서 무엇을 만드는 줄인가?
  • 지금 이 변수 안에 실제로 든 값은 무엇인가? (print로 찍어 본다)
  • 이 이름은 어디서 만들어졌나? (위의 4곳)
  • 이 함수의 def 줄 괄호는 몇 칸이고 어떤 순서인가?
  • 같은 모양의 다른 줄이 이미 맞게 쓰여 있나? 있으면 그 줄을 따라 쓴다.

예: 값이 어디서 오나 (실제로 헷갈렸던 줄)

restore_action = choose_restore_action(request["action"]) 이 줄을 말로 풀면 이렇다.

  • restore_action = : 결과를 담을 이름이다. 왼쪽은 내가 지은 이름.
  • choose_restore_action( : 이미 위에 만들어 둔 함수를 부른다.
  • request["action"] : 그 함수에 넣을 재료. request는 def 괄호에서 온 서랍장이고, 그 안의 "action" 칸을 연 것이다.
  • 코드에는 "request의" 같은 한국어 조사가 없다. 서랍장 이름 뒤에 ["칸 이름"]을 붙이는 것이 "의"이다.

실제 값으로 따라가면 이렇다.

  • request에 {"event_id":"EVT-001", "action":"block_ip", ...}가 들어 있다.
  • request["action"]은 글자 "block_ip"가 된다.
  • choose_restore_action("block_ip")은 글자 "unblock_ip"를 돌려준다.
  • 그래서 줄이 끝나면 restore_action 안에는 "unblock_ip"가 들어 있다.

if __name__ == "__main__": 가 뭔가 (실제 파일 classifier.py로 따라가기)

__name__은 파이썬이 파일마다 자동으로 붙여 주는 이름이다. 값은 두 경우로 나뉜다.

  • 경우 1 : classifier.py를 직접 실행한다 (VS Code에서 ▶). 이때 __name__은 "__main__"이다.
  • 경우 2 : 다른 파일이 from classifier import event_check를 한다. 이때 classifier.py 안의 __name__은 "classifier"다.

playbook.py 맨 위에 실제로 from classifier import event_check가 있다. 그래서 playbook.py를 실행하면 classifier.py가 경우 2로 읽힌다.

classifier.py 맨 아래는 if __name__ == "__main__": 아래에 detections.json을 읽는 줄과 print하는 for문이 있다.

  • 경우 1 : 조건이 참이라 아래가 실행된다. EVT-001 즉시 자동조치 같은 줄이 나온다.
  • 경우 2 : 조건이 거짓이라 아래는 건너뛴다. 파일을 읽지도, 출력하지도 않는다.

이게 필요한 이유는 두 가지다. 실제로 겪은 일이다.

  • 조건이 없으면 playbook.py를 실행할 때 classifier.py의 detections.json 읽기가 같이 실행된다. 그 파일이 없는 폴더에서는 FileNotFoundError로 멈춘다.
  • 조건이 없으면 classifier.py의 for문 출력이 playbook.py의 실행 화면에 섞여 나온다.

확인 문제 : playbook.py를 직접 실행하면, playbook.py 안의 __name__은 무엇일까? 답은 "__main__"이다. 그래서 playbook.py 맨 아래 테스트는 실행된다.

2. 1번 classifier.py▲ 맨 위

한눈에 보기

이벤트 1건을 받아 대응 등급 글자 1개를 돌려준다.

  • 즉시 자동조치 : 사람 확인 없이 바로 막는다
  • 승인 후 조치 : 사람이 승인하면 막는다
  • 모니터링만 : 막지 않고 지켜본다

함수는 2개다.

  • check_vip(src_ip, user, vip_data) : VIP인가? True 또는 False만 돌려준다.
  • event_check(user, src_ip, risk_score, rule, vip_data) : 등급 글자를 돌려준다.

받아 오는 파일 2개 (맨 아래 테스트에서만 읽는다)

  • detections.json : 2파트가 만든 이벤트 목록.
  • vip_accounts.json : VIP 명단.

왜 이렇게 나눴나

  • VIP 확인과 등급 정하기는 다른 일이다. VIP 기준이 바뀌면 check_vip만 고치면 된다.
  • 규칙이 "점수로 기본 등급 → VIP면 낮춘다" 두 단계다. 코드 순서도 같게 했다.
  • 중간에 return 하면 거기서 함수가 끝나서 아래 VIP 검사가 실행되지 않는다. 그래서 level에 적어 두고 마지막에 한 번만 return 한다.
  • 큰 점수부터 물어야 한다. elif는 처음 맞는 하나만 실행하기 때문이다.

문제 문장 → 코드 모양

문제 문장 : "점수가 80 이상이면 즉시 자동조치, 50 이상이면 승인 후 조치, 나머지는 모니터링만. 단, 80 이상이어도 VIP면 승인 후 조치."

  • "A면 X, B면 Y, 나머지는 Z" → if / elif / else, 큰 점수부터
  • "단, ~이어도 VIP면" → 먼저 기본값을 level에 적고, 그 아래에 고치는 if를 한 번 더
  • "VIP인가?" → 따로 함수 check_vip, 돌려주는 것은 True / False
  • "목록 안에 있나?" → in
  • "계정 이름으로 칸을 찾는다" → vip_data["vip_users"]

전체 코드 (주석 포함)

# =====================================================================
# classifier.py  (4파트 대응·리포트 - 1번 파일)
#
# 이 파일이 하는 일
#   탐지 이벤트 1건의 위험 점수를 보고 "대응 등급" 글자 1개를 정한다.
#     "즉시 자동조치" : 사람 확인 없이 바로 막는다
#     "승인 후 조치"  : 사람이 승인하면 막는다
#     "모니터링만"    : 막지 않고 지켜본다
#   이 글자 3개는 팀 표준이다. 띄어쓰기까지 똑같이 써야 한다.
#   (1·3파트 코드와 2번 playbook.py가 이 글자를 그대로 비교한다. 한 글자라도 다르면 안 된다.)
#
# 이 파일이 "받아 오는 것" (값의 출처)
#   함수 안에서는 파일을 읽지 않는다. 값은 전부 def 괄호로 받는다.
#   받는 값의 원래 출처는 이렇다.
#     detections.json   : 2파트(탐지)가 만든 이벤트 목록 (공통로그 2번 형식)
#                         이 파일에서는 맨 아래 테스트에서만 읽는다.
#     vip_accounts.json : VIP 명단 파일. {"vip_users": [...], "vip_ips": [...]} 모양.
#                         이 파일에서는 맨 아래 테스트에서만 읽는다.
#   실제 서비스에서는 main.py가 두 파일을 읽어서 이 파일의 함수에 넣어 준다.
#
# 이 파일이 "내보내는 것"
#   event_check(...)가 돌려주는 등급 글자 1개
#   -> 2번 playbook.py가 `from classifier import event_check`로 가져가 쓴다.
#
# 주석 표시 약속
#   [뭐함] 이 줄(덩어리)이 하는 일
#   [출처] 이 이름의 값이 어디서 오는지
#   [흐름] 실제 값을 넣으면 어떻게 돌아가는지
#   [왜]   왜 필요한지
# =====================================================================

import json     # [뭐함] json 파일을 읽는 도구를 가져온다. 맨 아래 테스트의 json.load가 이 도구다.
                # [왜]   파일 맨 위에서 가져와야 아래 코드가 쓸 수 있다.


# ---------------------------------------------------------------------
# 1. check_vip : 이 계정(또는 IP)이 VIP인가?
# ---------------------------------------------------------------------
def check_vip(src_ip, user, vip_data):
    # [뭐함] VIP이면 True, 아니면 False를 돌려준다. (등급 글자는 여기서 정하지 않는다)
    # [출처] 괄호 안 세 이름은 이 함수를 부르는 쪽이 값을 넣어 준다.
    #        부르는 곳: 이 파일의 event_check 안 (아래 2번 함수)
    #          src_ip   : 이벤트의 src_ip 칸 (detections.json -> 공통로그 2번)
    #          user     : 이벤트의 user 칸    (detections.json -> 공통로그 2번)
    #          vip_data : vip_accounts.json을 읽어 만든 서랍장 (dict)
    #        주의: 괄호 순서가 (src_ip, user, vip_data)다. event_check의 순서(user, src_ip)와 다르다.
    # [흐름] check_vip("192.168.30.12", "emp3", vip_data)
    #        -> "emp3"는 vip_users에 없고 IP도 vip_ips에 없다 -> False

    if user in vip_data["vip_users"]:      # [뭐함] vip_data의 "vip_users" 서랍을 열어 user가 그 안에 있나 본다
        return True
    elif src_ip in vip_data["vip_ips"]:    # [뭐함] 아니면 "vip_ips" 서랍에 src_ip가 있나 본다
        return True
    else:                                  # [뭐함] 둘 다 아니면
        return False


# ---------------------------------------------------------------------
# 2. event_check : 대응 등급 정하기
# ---------------------------------------------------------------------
def event_check(user, src_ip, risk_score, rule, vip_data):
    # [뭐함] 이벤트 1건의 정보를 받아 등급 글자 1개를 돌려준다.
    # [출처] 괄호 안 다섯 이름의 값은 부르는 쪽이 넣어 준다.
    #        부르는 곳 1: 이 파일 맨 아래 테스트 for문 (event["user"] 등을 꺼내서 넣는다)
    #        부르는 곳 2: playbook.py의 run_playbook (event["user"] 등을 꺼내서 넣는다)
    #          user       : 이벤트의 user 칸       (2파트 공통로그 2번)
    #          src_ip     : 이벤트의 src_ip 칸     (2파트 공통로그 2번)
    #          risk_score : 이벤트의 risk_score 칸 (2파트가 계산한 위험 점수, 숫자)
    #          rule       : 이벤트의 rule 칸       (탐지 규칙 이름. 지금은 계산에 안 쓴다.
    #                       다른 파일과 칸을 맞추려고 받기만 한다)
    #          vip_data   : vip_accounts.json을 읽은 서랍장 (main.py가 읽어서 넘긴다)
    # [규칙] 점수 80 이상 -> 즉시 자동조치 / 50 이상 -> 승인 후 조치 / 나머지 -> 모니터링만
    #        단, 80 이상이어도 VIP면 승인 후 조치로 낮춘다.
    # [왜]   VIP 계정을 컴퓨터가 마음대로 막으면 큰 사고가 나므로 사람 승인을 거친다.

    # (1) 점수로 기본 등급을 level에 적는다.
    # [왜] 큰 점수부터 물어야 한다. if/elif는 위에서부터 처음 맞는 하나만 실행한다.
    #      90점을 ">= 50"부터 물으면 "승인 후 조치"에서 끝나 버린다.
    if risk_score >= 80:
        level = "즉시 자동조치"
    elif risk_score >= 50:
        level = "승인 후 조치"
    else:
        level = "모니터링만"

    # (2) 80점 이상인데 VIP이기까지 하면 level을 "승인 후 조치"로 고친다.
    # [출처] check_vip은 바로 위 1번 함수다. 괄호 순서 (src_ip, user, vip_data)를 맞춰 부른다.
    if risk_score >= 80 and check_vip(src_ip, user, vip_data) == True:
        level = "승인 후 조치"

    # (3) 마지막에 한 번만 돌려준다.
    # [왜] 위에서 바로 return 하면 거기서 함수가 끝나서 (2)번 VIP 검사가 실행되지 않는다.
    return level
    # [흐름] EVT-001(emp3, 점수 90): (1)에서 "즉시 자동조치" -> (2) VIP 아님 -> 그대로 돌려줌
    #        EVT-006(admin, 점수 90): (1)에서 "즉시 자동조치" -> (2) VIP -> "승인 후 조치"로 고침


# ---------------------------------------------------------------------
# 테스트용 (이 파일을 직접 실행할 때만 돈다)
# ---------------------------------------------------------------------
# [뭐함] __name__ 은 파이썬이 파일마다 자동으로 붙여 주는 이름이다.
#        이 파일을 직접 실행(VS Code의 ▶)하면 __name__ 이 "__main__" 이 되어 아래가 실행된다.
#        다른 파일이 `import classifier` 하면 __name__ 이 "classifier" 가 되어 아래는 실행되지 않는다.
# [왜]   이 조건이 없으면 두 가지 문제가 생긴다.
#        1) 다른 파일이 import 할 때마다 detections.json을 읽는다.
#           그 파일이 없는 폴더에서는 FileNotFoundError 로 프로그램이 멈춘다.
#        2) 테스트 for문의 출력("EVT-001 즉시 자동조치" 같은 줄)이 다른 파일의 실행 화면에 섞여 나온다.
if __name__ == "__main__":
    with open("detections.json", "r", encoding="utf-8") as file:   # [뭐함] 읽기("r")로 열고 file이라고 부른다
                                                 # [왜] encoding="utf-8" : 한글이 든 json을 윈도우에서 읽을 때 생기는
                                                 #      UnicodeDecodeError(cp949)를 막는다. 팀 파일은 utf-8로 저장한다.
        detections = json.load(file)             # [출처] 2파트가 만든 이벤트 목록(list)이 detections에 담긴다
                                                 # [흐름] 이벤트 7건이면 detections는 7칸짜리 목록

    with open("vip_accounts.json", "r", encoding="utf-8") as file: # [뭐함] 앞 with가 끝나서 file 이름을 다시 써도 된다
        vip_data = json.load(file)               # [출처] VIP 명단 서랍장(dict)이 vip_data에 담긴다
                                                 # [흐름] {"vip_users": ["admin"], "vip_ips": []}

    for event in detections:                     # [뭐함] 이벤트를 하나씩 꺼내 event라고 부른다
        result = event_check(event["user"], event["src_ip"], event["risk_score"],
                             event["rule"], vip_data)
                                                 # [출처] 괄호 안 순서는 event_check의 def 줄
                                                 #        (user, src_ip, risk_score, rule, vip_data)과 같다
        print(event["event_id"], result)         # 예: EVT-001 즉시 자동조치

실행 따라가기

EVT-001 (emp3, 192.168.30.12, 점수 90, VIP 명단은 admin 하나)

  • event_check("emp3", "192.168.30.12", 90, "failed_login_5_in_10min", vip_data)가 불린다. user에 "emp3", risk_score에 90이 들어온다.
  • 90 >= 80이 참이라 level = "즉시 자동조치". elif, else는 건너뛴다.
  • 90 >= 80이 참이므로 check_vip(...)가 불린다. emp3는 VIP 계정이 아니고 IP도 VIP IP가 아니라 False.
  • False == True는 거짓이라 level은 그대로. return level → "즉시 자동조치".

EVT-006 (admin, 점수 90)

  • 위와 같이 level = "즉시 자동조치". check_vip에서 "admin"이 VIP 계정 목록에 있어 True.
  • level을 "승인 후 조치"로 다시 적고 돌려준다.

실제로 한 실수 (다시 하지 않기)

  • 점수 판정에서 바로 return : VIP 검사가 실행되지 않는다. → level = ...에 담고 마지막에 return level
  • for vip_user in vip_data : for는 서랍 이름표("vip_users")를 꺼낸다. 사람 이름이 아니다. → if user in vip_data["vip_users"]
  • if user in vip_data: : 서랍장에서 이름표 글자만 찾는다. → 서랍을 열어 vip_data["vip_users"]
  • 등급 글자를 즉시차단, 이상으로 쓴 것 : 팀 표준과 다르다. → 표준 3개로 통일
  • if check_vip = True : =는 넣기, 비교는 ==. 함수는 괄호와 재료를 넣어 불러야 한다. → check_vip(src_ip, user, vip_data) == True
  • if 아래를 비워 둔 것 : 실행할 줄이 없으면 에러
  • 파일 읽기와 테스트 for문을 if __name__ == "__main__": 밖에 둔 것 : playbook.py가 import 할 때 detections.json이 없으면 FileNotFoundError가 나고, 출력이 섞인다. → 전부 if __name__ == "__main__": 아래로 옮겼다. (2026-10-26에 고침)

3. 2번 playbook.py▲ 맨 위

한눈에 보기

세 가지 일을 한다.

  • 1번이 정한 등급 글자를 받는다.
  • 이벤트의 상태를 statuses 서랍장에 적는다.
  • 1·3파트가 읽을 조치 요청 6칸(공통로그 3번)을 만든다.

함수는 6개다.

  • choose_action(event_type) : 이벤트 유형 → 조치 이름
  • choose_target(action, user, src_ip) : 조치 이름 → 대상
  • make_request(event, level, dry_run) : 조치 요청 6칸 만들기
  • first_status(level) : 등급 → 처음 상태
  • apply_result(statuses, result) : 조치 결과 → 상태 바꾸기
  • run_playbook(event, vip_data, statuses) : 위 함수들을 이어 붙이는 입구

왜 이렇게 나눴나

  • 1번은 등급만 정한다. 등급만으로는 아무것도 실행되지 않는다. 1·3파트는 무슨 조치를, 누구에게 하는지 알아야 한다.
  • 이름 정하는 일(action)과 대상 정하는 일(target)이 다르다. 그래서 함수를 둘로 나눴다.
  • apply_result는 return이 없다. 서랍장은 함수 안에서 바꾸면 바깥 서랍장도 같이 바뀌기 때문이다.
  • run_playbook은 다른 함수를 부르기만 한다. 6단계의 "이어 붙이기"다.

출력 칸마다 "어디서 오나?" (2단계 연습)

조치 요청 6칸의 값이 어디서 오는지 하나씩 묻는다.

  • event_id : 이벤트에 있다. event["event_id"] (곳 3)
  • reason : 이벤트의 rule을 그대로 쓴다. event["rule"] (곳 3)
  • action : 이벤트에 없다. 유형을 보고 정해야 한다. 그래서 함수 choose_action이 필요하다.
  • target : 이벤트에 없다. action에 따라 user나 src_ip를 골라야 한다. 그래서 함수 choose_target이 필요하다.
  • response_level : 이벤트에 없다. 1번이 정한 값이다. 그래서 def 괄호로 받는다. (곳 1)
  • dry_run : 이벤트에도 없고 만들 수도 없다. 부르는 쪽이 정해 준다. def 괄호로 받는다. (곳 1)

이 질문만 칸마다 던지면 "어떤 함수가 필요한가"가 저절로 나온다. 입력에 있으면 꺼내고, 계산해야 하면 함수를 만들고, 둘 다 아니면 괄호로 받는다.

전체 코드 (주석 포함)

# =====================================================================
# playbook.py  (4파트 대응·리포트 - 2번 파일)
#
# 이 파일이 하는 일 (세 가지)
#   1) 1번 classifier.py가 정한 대응 등급 글자를 받는다.
#   2) 이벤트가 지금 어느 단계인지(상태)를 statuses 서랍장에 적는다.
#   3) 1·3파트가 읽고 실행할 "조치 요청"(공통로그 3번, 6칸)을 만든다.
#
# 이 파일이 "받아 오는 것" (값의 출처)
#   classifier.py   : from classifier import event_check
#                     -> 등급 글자를 구하는 함수를 가져온다.
#                     (classifier.py는 import 해도 json 파일을 읽지 않는다)
#   event           : 2파트가 만든 detections.json의 이벤트 1건 (공통로그 2번).
#                     main.py가 목록에서 하나씩 꺼내 run_playbook에 넣어 준다.
#   vip_data        : vip_accounts.json을 읽은 서랍장. main.py가 읽어 넘긴다.
#   statuses        : {이벤트번호: 상태} 서랍장. main.py가 빈 {}로 만들어 계속 넘겨 준다.
#   result          : 1·3파트가 조치 실행 뒤 돌려주는 조치 결과 (공통로그 5번).
#
# 이 파일이 "내보내는 것"
#   run_playbook(...)   -> 조치 요청 서랍장 6칸 (또는 None). 1·3파트가 읽는다.
#                          또 statuses에 이 이벤트의 처음 상태를 적는다.
#   apply_result(...)   -> 돌려주는 값은 없고 statuses의 상태를 바꾼다.
#   (조치 요청은 3번 false_positive.py와 4번 ticket.py의 재료이기도 하다)
#
# 팀 표준 글자 (띄어쓰기까지 그대로)
#   등급 : 즉시 자동조치 / 승인 후 조치 / 모니터링만
#   상태 : 신규 / 승인대기 / 조치중 / 완료 / 실패 / 모니터링
#   결과 : success / fail / skipped / approval_required
#
# 주석 표시 약속
#   [뭐함] 이 줄(덩어리)이 하는 일   [출처] 값이 어디서 오는지
#   [흐름] 실제 값을 넣으면 어떻게 돌아가는지   [왜] 왜 필요한지
# =====================================================================

import json
from classifier import event_check
# [뭐함] classifier.py 파일 안의 event_check 함수를 이 파일로 가져온다.
# [왜]   등급 정하는 일은 1번 파일이 이미 한다. 다시 쓰지 않고 가져다 쓴다.
# [주의] classifier.py가 이 파일과 같은 폴더에 있어야 한다.
# [참고] import json 은 맨 아래 테스트에서는 쓰지 않는다. 지워도 동작은 같다.


# ---------------------------------------------------------------------
# 1. choose_action : 이벤트 유형 -> 조치(action) 이름
# ---------------------------------------------------------------------
def choose_action(event_type):
    # [뭐함] 이벤트 유형 글자를 받아 조치 이름 글자를 돌려준다. 모르는 유형이면 None.
    # [출처] event_type : 부르는 곳은 아래 3번 make_request.
    #        값은 이벤트의 event_type 칸 (2파트 공통로그 2번)
    #        ABNORMAL_LOGIN / OFFHOUR_LOGIN / UNAUTHORIZED_ACCESS /
    #        MALICIOUS_IP / TRAFFIC_SPIKE / CORRELATED_ATTACK 중 하나
    # [왜]   조치를 실행하는 1·3파트는 "무슨 조치인지" 글자를 보고 움직이므로 우리가 정해서 넘긴다.
    # [흐름] "OFFHOUR_LOGIN" -> 두 번째 elif에 맞아 "terminate_session" 돌려주고 끝

    if event_type in ["ABNORMAL_LOGIN", "TRAFFIC_SPIKE", "CORRELATED_ATTACK", "MALICIOUS_IP"]:
        return("block_ip")             # IP 차단 : 3파트가 실행한다
    elif event_type == "OFFHOUR_LOGIN":
        return("terminate_session")    # 세션 종료 : 1파트가 실행한다
    elif event_type == "UNAUTHORIZED_ACCESS":
        return("lock_account")         # 계정 잠금 : 1파트가 실행한다
    else:
        return None                    # 규칙에 없는 유형. 아래 run_playbook이 None을 보고 요청을 만들지 않는다


# ---------------------------------------------------------------------
# 2. choose_target : 조치(action) -> 조치 대상(target)
# ---------------------------------------------------------------------
def choose_target(action, user, src_ip):
    # [뭐함] 조치 이름에 맞는 대상(IP 또는 계정)을 돌려준다.
    # [출처] action : 바로 위 1번 함수가 돌려준 값 (make_request 안에서 변수 action에 담긴 것)
    #        user, src_ip : 이벤트의 user, src_ip 칸 (2파트 공통로그 2번)
    # [왜]   IP를 막는 조치는 IP가, 계정에 하는 조치는 계정 이름이 필요하다.
    # [주의] 값이 필요하므로 return(src_ip)에 따옴표를 쓰지 않는다. 따옴표를 쓰면 "src_ip"라는 글자가 간다.
    # [흐름] action="block_ip", src_ip="192.168.30.12" -> "192.168.30.12" 돌려준다

    if action == "block_ip":
        return(src_ip)
    elif action in ["lock_account", "terminate_session"]:
        return(user)
    else:
        return None                    # action이 None이면 target도 None


# ---------------------------------------------------------------------
# 3. make_request : 조치 요청(공통로그 3번) 1건 만들기
# ---------------------------------------------------------------------
def make_request(event, level, dry_run):
    # [뭐함] 1·3파트에게 넘길 조치 요청 서랍장(6칸)을 만들어 돌려준다.
    # [출처] event   : 이벤트 1건. run_playbook(아래 6번)이 그대로 넘겨 준다. (2파트 공통로그 2번)
    #        level   : 대응 등급 글자. run_playbook이 classifier.event_check로 구한 값이다.
    #        dry_run : True면 "기록만, 실제 조치는 안 함", False면 진짜 실행.
    #                  run_playbook이 False를 넣어 준다. 입력에도 없고 만들 수도 없어서 괄호로 받는다.
    # [왜]   칸 이름 6개(event_id, action, target, response_level, reason, dry_run)는
    #        공통로그 3번이 정한 팀 표준이다. 1·3파트가 이 이름표로 값을 꺼내므로 바꾸면 안 된다.

    action = choose_action(event["event_type"])                      # 위 1번 함수에게 물어서 action에 담는다
    target = choose_target(action, event["user"], event["src_ip"])   # 위 2번 함수. 괄호 순서는 def (action, user, src_ip)와 같다

    request = {
        "event_id"       : event["event_id"],    # [출처] 이벤트에 있는 값을 그대로
        "action"         : action,               # [출처] 바로 위에서 구한 변수
        "target"         : target,               # [출처] 바로 위에서 구한 변수
        "response_level" : level,                # [출처] def 괄호로 받은 등급 글자
        "reason"         : event["rule"],        # [출처] 이벤트의 rule 칸(탐지 규칙 이름)을 이유로 쓴다
        "dry_run"        : dry_run               # [출처] def 괄호로 받은 값
    }
    return request                               # [주의] 함수 이름이 아니라 서랍장이 든 변수 request를 돌려준다
    # [흐름] event EVT-001(ABNORMAL_LOGIN, emp3, 192.168.30.12, rule=failed_login_5_in_10min),
    #        level="즉시 자동조치", dry_run=False 이면
    #        {"event_id":"EVT-001","action":"block_ip","target":"192.168.30.12",
    #         "response_level":"즉시 자동조치","reason":"failed_login_5_in_10min","dry_run":False}


# ---------------------------------------------------------------------
# 4. first_status : 대응 등급 -> 이벤트의 처음 상태
# ---------------------------------------------------------------------
def first_status(level):
    # [뭐함] 등급 글자를 받아 처음 상태 글자를 돌려준다.
    # [출처] level : run_playbook(아래 6번)이 event_check로 구해서 넘긴 등급 글자.
    # [주의] 점수(숫자)가 아니라 등급 글자를 비교한다.
    #        등급 글자는 "모니터링만", 상태 글자는 "모니터링"이다. 비교할 때는 등급 쪽을 쓴다.
    # [흐름] "승인 후 조치" -> "승인대기"

    if level == "즉시 자동조치":
        return("조치중")
    elif level == "승인 후 조치":
        return("승인대기")
    elif level == "모니터링만":
        return("모니터링")
    else:
        return("신규")                  # 정해진 등급이 아니면 신규


# ---------------------------------------------------------------------
# 5. apply_result : 조치 결과(공통로그 5번) -> 상태 바꾸기
# ---------------------------------------------------------------------
def apply_result(statuses, result):
    # [뭐함] 1·3파트가 돌려준 조치 결과를 보고 statuses의 상태를 바꾼다. return이 없다.
    # [출처] statuses : main.py가 만든 상태 서랍장. run_playbook이 이미 이 이벤트 칸을 만들어 두었다.
    #        result   : 1·3파트가 돌려준 조치 결과 1건 (공통로그 5번).
    #                   쓰는 칸은 두 개 : result["event_id"], result["result"]
    # [왜]   return이 없는 이유: 서랍장은 함수 안에서 바꿔도 바깥 서랍장이 같이 바뀐다.
    #        그래서 값을 돌려줄 필요가 없다.
    # [흐름] result = {"event_id":"EVT-003","result":"fail", ...}
    #        -> event_id="EVT-003", outcome="fail" -> statuses["EVT-003"] = "실패"

    event_id = result["event_id"]

    outcome = result["result"]         # success / fail / skipped / approval_required 중 하나

    if outcome == "success":
        statuses[event_id] = "완료"
    elif outcome == "fail":
        statuses[event_id] = "실패"
    elif outcome == "skipped":
        statuses[event_id] = "완료"        # 이미 처리되어 건너뜀 -> 일은 끝난 것으로 본다
    elif outcome == "approval_required":
        statuses[event_id] = "승인대기"


# ---------------------------------------------------------------------
# 6. run_playbook : 이벤트 1건 처리 (main.py가 부르는 입구)
# ---------------------------------------------------------------------
def run_playbook(event, vip_data, statuses):
    # [뭐함] 등급 구하기 -> 처음 상태 적기 -> (모니터링만이 아니면) 조치 요청 만들어 돌려주기.
    # [출처] event    : detections.json 목록에서 main.py가 하나 꺼낸 이벤트 (2파트 공통로그 2번)
    #        vip_data : vip_accounts.json을 읽은 서랍장 (main.py가 읽어 넘긴다)
    #        statuses : main.py가 만든 상태 서랍장. 이 함수가 이 이벤트의 처음 상태를 적는다.
    # [돌려주는 것] 조치 요청 서랍장 6칸. 아래 두 경우에는 None.
    #        1) 모니터링만 : 지켜보기만 하므로 요청이 없다
    #        2) event_type이 6개 목록에 없음 : 무슨 조치를 할지 정할 수 없다
    #        main.py는 None이 아닐 때만 1·3파트에게 넘기고 티켓을 만들어야 한다.

    event_id = event["event_id"]
    level = event_check(event["user"], event["src_ip"],
                        event["risk_score"], event["rule"],
                        vip_data)
    # [출처] 괄호 순서는 classifier.py의 def 줄 (user, src_ip, risk_score, rule, vip_data)과 같다.

    statuses[event_id] = first_status(level)   # = 은 오른쪽부터 계산한다. 상태 글자를 이 이벤트 칸에 넣는다

    if level == "모니터링만":
        return None                            # 지켜보기만 하므로 조치 요청을 만들지 않는다
    else:
        request = make_request(event, level, False)   # dry_run은 기본값 False(진짜 실행)
        if request["action"] is None:
            # [왜] event_type이 6개 목록에 없으면 choose_action이 None을 돌려줘서 action도 None이다.
            #      이 요청을 그대로 돌려주면 1·3파트가 "무슨 조치인지" 몰라서 멈춘다.
            #      그래서 요청을 만들지 않고, 상태를 "조치중"이 아니라 "신규"로 되돌려 둔다.
            statuses[event_id] = "신규"
            return None
        return request
    # [흐름] EVT-004(점수 낮음) -> level="모니터링만" -> statuses["EVT-004"]="모니터링" -> None
    #        EVT-001(점수 90)   -> level="즉시 자동조치" -> statuses["EVT-001"]="조치중" -> 요청 6칸
    #        type이 suspicious_login인 이벤트 -> action이 None -> statuses는 "신규" -> None

# 테스트용 (이 파일을 직접 실행할 때만 돈다. 왜 이렇게 하는지는 classifier.py 맨 아래 주석 참고)
# ---------------------------------------------------------------------
if __name__ == "__main__":
    # [뭐함] 함수 1, 2가 맞는지 값 하나씩 넣어 본다.
    print(choose_action("MALICIOUS_IP"))                         # 기대: block_ip
    print(choose_target("block_ip", "emp3", "192.168.30.12"))    # 기대: 192.168.30.12
    print(choose_target("lock_account", "emp3", "192.168.30.12"))# 기대: emp3

    # [출처] 아래 test_event의 값은 내가 정한 테스트 값이다.
    #        칸 이름은 공통로그 2번에서, EVT-001, failed_login_5_in_10min, ABNORMAL_LOGIN, emp3,
    #        192.168.30.12는 공통로그 2번 그림의 예시에서 가져왔다. risk_score 80은 테스트용이다.
    test_event = {"event_id": "EVT-001", "rule": "failed_login_5_in_10min", "event_type": "ABNORMAL_LOGIN", "user": "emp3", "src_ip": "192.168.30.12", "risk_score": 80}
    vip_data = {"vip_users": ["admin"], "vip_ips": []}    # VIP 명단 모양 (vip_accounts.json과 같은 모양)
    statuses = {}                                          # 상태 서랍장은 빈 {}로 시작한다
    print(run_playbook(test_event, vip_data, statuses))    # 기대: 요청 6칸 서랍장
    print(statuses)                                        # 기대: {'EVT-001': '조치중'}

    # [뭐함] 6개 목록에 없는 event_type이 오면 None이 나오고 상태가 "신규"인지 본다.
    unknown_event = {"event_id": "EVT-002", "rule": "x", "event_type": "suspicious_login", "user": "emp4", "src_ip": "192.168.30.13", "risk_score": 90}
    print(run_playbook(unknown_event, vip_data, statuses)) # 기대: None
    print(statuses)                                        # 기대: {'EVT-001': '조치중', 'EVT-002': '신규'}

    # [뭐함] 조치 결과가 success로 오면 EVT-001이 "완료"로 바뀌는지 본다.
    apply_result(statuses, {"event_id": "EVT-001", "result": "success"})
    print(statuses)                                        # 기대: {'EVT-001': '완료', 'EVT-002': '신규'}

함수마다 생각하는 순서

  • choose_action : 받는 것은 글자 하나, 돌려주는 것도 글자 하나. 같은 action이 나오는 유형 4개는 목록으로 묶고 in으로 묻는다. 나머지는 ==. 아무것도 안 맞으면 None.
  • choose_target : block_ip는 IP를 막는 것이니 src_ip. 계정에 하는 조치 둘은 user. 나머지 None. 값이 필요하므로 따옴표를 쓰지 않는다.
  • make_request : 먼저 action, target을 구해서 변수에 담는다. 서랍장 이름표 6개는 공통로그 3번 예시에서 옮겨 쓴다. 오른쪽 값은 칸마다 "어디서 오나?"를 묻는다.
  • first_status : 입력은 점수가 아니라 등급 글자다. 3개를 if / elif / elif로 비교하고 어디에도 안 맞으면 "신규".
  • apply_result : 결과 서랍장에서 event_id, result를 꺼내고, 값에 따라 statuses[event_id] = 상태를 넣는다.
  • run_playbook : event_id를 꺼낸다 → 1번 event_check로 등급을 구한다 → statuses[event_id] = first_status(level) → 모니터링만이면 None → 아니면 make_request(event, level, False)로 요청을 만든다 → 요청의 action이 None이면 상태를 "신규"로 되돌리고 None을 돌려준다 → 아니면 요청을 돌려준다.

실행 따라가기

EVT-001 (점수 90, emp3, VIP 아님)이 run_playbook에 들어갔을 때

  • event_id = event["event_id"] → "EVT-001"
  • event_check(...) 안으로 들어간다. 1번에서 본 대로 "즉시 자동조치"를 들고 나와 level에 담긴다.
  • statuses[event_id] = first_status(level) : =는 오른쪽부터 계산한다. first_status("즉시 자동조치")는 "조치중". 그 값을 statuses["EVT-001"] 칸에 넣는다.
  • level == "모니터링만"은 거짓이라 else로 간다.
  • make_request(event, level, False) 안에서 choose_action("ABNORMAL_LOGIN") → "block_ip", choose_target("block_ip", "emp3", "192.168.30.12") → "192.168.30.12". 6칸 서랍장이 만들어져 돌아온다.
  • request["action"]이 "block_ip"이므로 None이 아니다. 요청을 돌려준다.

EVT-006 (admin, 점수 90)이면 1번이 "승인 후 조치"를 돌려주므로 상태는 "승인대기"가 된다.

유형이 suspicious_login인 이벤트면 choose_action이 None을 돌려줘서 요청의 action이 None이 된다. 그러면 상태를 "신규"로 되돌리고 None을 돌려준다.

실제로 한 실수 (다시 하지 않기)

  • event_type == "A" or "B" : or 뒤 글자는 항상 참으로 읽힌다. → event_type in ["A", "B"]
  • 목록 글자 사이에 쉼표 없음 : 글자가 이어 붙는다.
  • return("src_ip") : 따옴표가 있으면 글자 그대로 간다. → return(src_ip)
  • "action": action["block_ip"] : 글자 하나가 든 변수에 대괄호를 붙였다. → "action": action
  • 서랍장 항목 끝 쉼표 빠짐 : 마지막 항목만 쉼표가 없다.
  • event "rule" : 대괄호 없음. → event["rule"]
  • "reason": rule : rule이라는 변수가 없다. → event["rule"]
  • return make_request : 함수 이름을 돌려준다. → return request
  • return(statuses[event_id("완료")]) : return은 서랍장을 바꾸지 못한다. → statuses[event_id] = "완료"
  • statuses[event_id:"완료"] : 콜론은 새로 만들 때 쓴다. → 칸을 닫고 = 뒤에 값
  • event["user", "src_ip", ...] : 대괄호는 이름표 하나만 받는다. 값마다 따로.
  • level == "모니터링" : level에는 등급 글자가 있다. → "모니터링만"
  • make_request[event, level, False] : 함수 실행은 소괄호.

오탐 규칙을 말로 먼저 적고 코드 모양으로 바꿨다.

  • "연습 실행(dry_run)이었으면 복구하지 않는다." → if request["dry_run"] == True: return None
  • "되돌릴 방법이 없으면 복구하지 않는다." → if restore_action == None: return None

  • "기록 한 건을 만든다." → 서랍장 9칸 (함수 3)

  • "복구와 기록을 한 번에." → 위 함수들을 순서대로 부르기만 하는 함수 (함수 5)

  • 복구 요청 6칸 중 event_id, target은 원래 요청과 같은 이벤트·같은 대상이므로 request["event_id"], request["target"]을 그대로 옮긴다.
  • 바뀌는 칸은 action(되돌리는 조치)과 reason("false_positive") 둘뿐이다.
  • 함수 3의 기록 9칸 중 risk_score 등 6개는 def 괄호에서 오고, detected_as_anomaly는 항상 True, is_actual_anomaly는 항상 False, recorded_at은 함수 안 첫 줄에서 만든 current_time이다.
  • 이벤트에서는 계정 칸 이름이 user인데, 기록에서는 username이다. 이름이 달라도 값은 같다. 이 연결은 함수 5에서 한다: event["user"]를 username 자리에 넣는다.
  • 시각은 datetime.now()만 쓰면 글자가 아니라 시각 덩어리라서 json에 저장할 때 에러가 난다. .strftime("%Y-%m-%d %H:%M:%S")로 글자로 바꾼다.

# ---------------------------------------------------------------------
# 함수 1. choose_restore_action
# ---------------------------------------------------------------------
def choose_restore_action(action):
    # [뭐함] 원래 조치 글자를 받아서, 그걸 되돌리는 조치 글자를 돌려준다.
    # [값의 출처] action : def 괄호. 부르는 곳은 아래 make_restore_request이고,
    #            값은 원래 조치 요청의 action 칸(request["action"])이다.
    # [왜]   "무엇의 반대가 무엇인지"를 한 곳에만 적어 두면 틀릴 일이 없다.
    # [흐름] action = "block_ip"           -> "unblock_ip" 돌려주고 끝
    #        action = "lock_account"       -> "unlock_account" 돌려주고 끝
    #        action = "terminate_session"  -> 위 둘이 아니므로 None 돌려주고 끝

    if action == "block_ip":                 # [뭐함] 원래 조치가 IP 차단이면
        return("unblock_ip")                 #        IP 차단 해제로 되돌린다
    elif action == "lock_account":           # [뭐함] 아니고, 계정 잠금이면
        return("unlock_account")             #        계정 잠금 해제로 되돌린다
    else:                                    # [뭐함] 둘 다 아니면
        return None                          # [왜] terminate_session은 이미 끊은 접속을
                                             #      되돌릴 방법이 없다. None은 "되돌릴 게 없다"는 표시다.


# ---------------------------------------------------------------------
# 함수 2. make_restore_request
# ---------------------------------------------------------------------
def make_restore_request(request, result):
    # [뭐함] 복구 요청 서랍장(6칸)을 만들어 돌려준다. 복구할 게 없으면 None을 돌려준다.
    # [값의 출처]
    #   request : playbook.py가 만든 원래 조치 요청 (칸 6개: event_id, action, target,
    #             response_level, reason, dry_run)
    #   result  : 1·3파트가 돌려준 조치 결과 (그 안의 "result" 칸이 success/fail 등의 글자)
    # [왜]   복구 요청은 "원래 조치가 실제로 성공했을 때만" 의미가 있다.
    #        안 걸린 조치를 풀려고 하면 오히려 오류가 난다.
    # [흐름] (예) request의 action이 "block_ip", result의 "result"가 "success"
    #        -> 3개의 if를 모두 통과 -> unblock_ip 복구 요청을 돌려준다.

    # [뭐함] 되돌리는 조치 글자를 함수 1에게 받아서 restore_action에 담는다.
    # [흐름] request["action"]이 "block_ip"이면 restore_action에는 "unblock_ip"가 담긴다.
    # [왜]   글자를 직접 적지 않고 함수에게 받는 이유: 요청마다 action이 다르기 때문이다.
    restore_action = choose_restore_action(request["action"])

    # [뭐함] 조치 결과가 success가 아니면 복구하지 않는다.
    # [왜]   fail            : 조치가 걸리지 않았으니 되돌릴 게 없다.
    #        skipped         : 실행하지 않았으니 되돌릴 게 없다.
    #        approval_required: 아직 승인 대기라 실행 전이다.
    if result["result"] != "success":
        return None

    # [뭐함] 원래 요청이 dry_run(연습 실행)이었으면 복구하지 않는다.
    # [왜]   dry_run이 True면 실제 조치 없이 기록만 했으므로 되돌릴 것이 없다.
    if request["dry_run"] == True:
        return None

    # [뭐함] 되돌리는 조치가 없으면(None) 복구하지 않는다.
    # [왜]   terminate_session 같은 조치는 함수 1이 None을 돌려준다.
    if restore_action == None:
        return None

    # [뭐함] 세 검사를 모두 통과했으니 복구 요청 서랍장 6칸을 만든다.
    # [왜]   1·3파트가 읽는 조치 요청 형식(6칸)과 똑같이 만들어야 그대로 실행할 수 있다.
    data = {
        "event_id": request["event_id"],       # 원래 요청과 같은 이벤트라서 그대로 옮긴다
        "action": restore_action,              # 바뀐 칸 1 : 되돌리는 조치 글자
        "target": request["target"],           # 같은 대상(IP 또는 계정)을 풀어야 하므로 그대로 옮긴다
        "response_level": "즉시 자동조치",       # 팀 표준 글자. 띄어쓰기까지 정확히 이대로
        "reason": "false_positive",            # 바뀐 칸 2 : 오탐 때문에 되돌린다는 이유
        "dry_run": request["dry_run"]          # 위 검사를 통과했으니 항상 False다
    }

    return(data)                               # [뭐함] 완성한 복구 요청을 돌려준다

# 함수 3. make_feedback

def make_feedback(event_id, username, event_type, risk_score, reason, confirmed_by):
    # [뭐함] 오탐 기록 한 건(9칸 서랍장)을 만들어 돌려준다.
    # [값의 출처] def 괄호의 6개 이름 + 아래에서 만드는 current_time
    #            부르는 곳은 handle_false_positive이고, event 서랍장에서 꺼내 넣는다.
    # [왜]   "탐지는 이상이라고 했지만 실제로는 정상이었다"는 증거를 남겨 두면
    #        나중에 탐지 규칙을 고칠 때 참고할 수 있다.
    # [흐름] (예) event_id="EVT-001", username="emp3", ... confirmed_by="admin"
    #        -> 9칸을 채워 돌려준다. 파일 저장은 함수 4가 한다.

    # [뭐함] 현재 시각을 "2026-10-25 00:07:42" 같은 글자로 current_time에 담는다.
    # [왜]   .strftime(...)이 없으면 글자가 아니라 시각 덩어리가 담겨서
    #        나중에 json 파일에 저장할 때 에러가 난다.
    current_time = datetime.now().strftime("%Y-%m-%d %H:%M:%S")

    data_1 = {
        "event_id": event_id,                    # def 괄호에서 온 값
        "username": username,                    # def 괄호에서 온 값
        "event_type": event_type,                # def 괄호에서 온 값
        "detected_as_anomaly": True,             # 항상 True : 탐지는 이상이라고 했다
        "risk_score": risk_score,                # def 괄호에서 온 값
        "is_actual_anomaly": False,              # 항상 False : 사람이 보니 정상이었다
        "false_positive_reason": reason,         # 이름표는 false_positive_reason, 값은 reason
        "confirmed_by": confirmed_by,            # 오탐이라고 확인한 사람
        "recorded_at": current_time              # 위에서 만든 현재 시각 글자
    }

    return(data_1)                               # [뭐함] 완성한 기록 한 건을 돌려준다

# 함수 4. save_feedback
# ---------------------------------------------------------------------
def save_feedback(feedback, filename):
    # [뭐함] 기록 한 건(feedback)을 json 파일의 목록 맨 뒤에 추가한다.
    # [값의 출처] feedback : 함수 3이 만든 서랍장 / filename : 파일 이름 글자
    # [왜]   파일에는 예전 기록이 쌓여 있다. 한 건만 새로 적으면 예전 기록이 사라진다.
    #        그래서 "읽기 -> 추가 -> 다시 쓰기" 순서로 한다.
    # [흐름] 처음(파일 없음)  : records = [] -> 한 건 추가 -> 1건짜리 파일이 생긴다.
    #        두 번째(1건 있음): records = [1건] -> 한 건 추가 -> 2건짜리 파일로 다시 쓴다.
    # 이 함수는 파일에 적기만 하므로 return이 없다.

    if os.path.exists(filename):                 # [뭐함] 파일이 있는지 먼저 확인한다.
                                                 # [왜]   처음에는 파일이 없다. 없는 파일을
                                                 #        "r"로 열면 에러가 나기 때문이다.
        with open(filename, "r", encoding="utf-8") as file:        # [뭐함] 읽기("r")로 연다
                                                 # [왜] encoding="utf-8" : 쓸 때와 읽을 때 방식을 같게 하고,
                                                 #      다른 파트(2파트)가 utf-8로 읽어도 한글이 안 깨지게 한다.
                                                 # [주의] 예전에 encoding 없이 만든 false_positive_feedback.json이
                                                 #        있으면 읽다가 UnicodeDecodeError가 난다. 그 파일을 지우고 다시 실행한다.
            records = json.load(file)            # [뭐함] 안에 있는 목록을 records에 담는다

                                                 # [왜]   "w"는 열면서 기존 내용을 전부 지운다.

def handle_false_positive(event, request, result, reason, confirmed_by):

    #        main.py는 오탐이 생기면 이 함수 하나만 부르면 된다.
    # [값의 출처]
    #   event        : 2파트가 준 탐지 이벤트 (event_id, user, event_type, risk_score가 필요)
    #   request      : 원래 조치 요청 (playbook.py가 만든 것)
    #   result       : 원래 조치 결과 (1·3파트가 돌려준 것)
    #   reason       : 오탐이라고 판단한 이유 (사람이 입력)
    #   confirmed_by : 오탐을 확인한 사람 (사람이 입력)
    # [왜]   복구는 조건이 안 맞으면 만들지 않지만, 기록은 오탐이면 항상 남겨야 한다.
    #        그래서 복구 결과와 상관없이 기록 저장까지 반드시 실행한다.
    # [흐름] 조치 성공(success): restore = 복구 요청 서랍장 -> 기록 저장 -> 복구 요청 돌려줌
    #        조치 실패(fail)   : restore = None            -> 기록 저장 -> None 돌려줌

    # [뭐함] 함수 2를 불러서 복구 요청(또는 None)을 restore에 담는다.
    restore = make_restore_request(request, result)

    feedback = make_feedback(event["event_id"], event["user"], event["event_type"], event["risk_score"], reason, confirmed_by)

    # [뭐함] 함수 4를 불러서 기록을 파일에 저장한다.
    save_feedback(feedback, "false_positive_feedback.json")

    # [뭐함] 복구 요청(또는 None)을 돌려준다. 이 요청을 1·3파트가 실행한다.
    return restore

                                                 # [왜]   json.load는 filename을 바꾸지 않는다. 읽은 내용을 담을 이름이 따로 필요하다.

    return(records)                              # [뭐함] 읽은 목록을 돌려준다 (파일 이름 글자가 아니다)

5. 4번 ticket.py▲ 맨 위

한눈에 보기

이벤트에 조치 요청이 있으면 티켓을 만들고, 조치 결과가 오면 티켓을 바꾸고, 담당자 알림 요청을 만든다.

함수는 3개다.

  • make_ticket(event, request, status) : 티켓 1장 만들기
  • update_ticket(ticket, result) : 조치 결과로 티켓 바꾸기
  • make_alert_request(event, level, message) : 알림 요청 4칸 만들기

받아 오는 것

  • event : 2파트 이벤트 1건 (공통로그 2번, 11칸 전부 필요)
  • request : 2번 run_playbook이 돌려준 조치 요청 (공통로그 3번)
  • status : 2번 statuses[event_id] 값. 이 파일은 상태를 직접 정하지 않는다.
  • result : 1·3파트가 돌려준 조치 결과 (공통로그 5번)

왜 이렇게 만들었나

  • 상태를 make_ticket 안에서 정하지 않고 def 괄호로 받는다. 상태를 정하는 곳을 playbook.py 한 군데로 두기 위해서다. 두 파일이 각자 정하면 상태가 어긋난다.
  • 티켓 안에 "event" 서랍과 "request" 서랍을 따로 넣는다. 5번 리포트가 이 티켓 하나만 보고 사고 개요, 탐지 근거, 조치 내역을 쓰게 하려고 했다.
  • "event" 서랍에 11칸을 다 넣는다. 이 중 rule, evidence는 리포트의 "탐지 근거"에 쓴다.
  • 조치 요청이 None이면(모니터링만, 또는 조치를 정할 수 없음) 티켓을 만들지 않는다. make_ticket은 request["action"]을 읽으므로 None을 받으면 에러가 난다. 그래서 6번 main.py에서 request가 None이 아닐 때만 부른다.
  • 알림 요청은 공통로그 4번 그림에 따라 4칸이다. 누가 이 함수를 부를지는 팀이 정해야 한다고 그림에 적혀 있다.

출력 칸마다 "어디서 오나?"

티켓의 바깥 칸 5개

  • ticket_id : "TKT-" + event["event_id"]. 함수 안 첫 줄에서 만든다. (곳 2)
  • status : def 괄호. (곳 1)
  • action_result : 아직 결과가 없으니 None. update_ticket이 채운다.
  • message : 마찬가지로 None. update_ticket이 채운다.
  • updated_at : 처음에는 탐지 시각 event["detected_at"]. update_ticket이 결과 시각으로 바꾼다.

알림 요청 4칸

  • event_id : event["event_id"] (곳 3)
  • level : def 괄호 (곳 1)
  • to : 위쪽 if/else에서 to = ...로 만든 이름 (곳 2). level이 1이면 "보안 담당자", 아니면 "보안팀장".
  • message : def 괄호 (곳 1)

문제 문장 → 코드 모양

  • "이벤트와 조치 요청에서 칸을 골라 티켓 서랍장을 만든다" → 서랍장 안에 서랍장({"event": {...}, "request": {...}, ...})
  • "결과 글자를 티켓에 적는다" → ticket["action_result"] = result["result"] (return 아님, 서랍장 바꾸기)
  • "성공이면 완료, 실패면 실패, 승인 필요면 승인대기, 그 외는 그대로" → if / elif / elif, 마지막 else는 아무것도 안 바꾼다
  • "1이면 보안 담당자, 아니면 보안팀장" → if level == 1: to = "보안 담당자" / else: to = "보안팀장"

#   make_ticket(...)        -> 티켓 서랍장 (아래 칸 목록 참고). 5번 report.py가 이 티켓으로 리포트를 만든다.
#   update_ticket(...)      -> 갱신된 티켓 (같은 서랍장이 바뀐 것)
#   make_alert_request(...) -> 알림 요청 서랍장 4칸 (공통로그 4번). 1파트가 읽는다.
#
# 티켓 칸 (make_ticket이 만든다)
#   "event"   서랍 : event_id, event_type, user, src_ip, risk_score, priority, asset,
#                    impact_scope, detected_at, rule, evidence      (공통로그 2번 11칸 전부)
#   "request" 서랍 : action, target, response_level, reason, dry_run (공통로그 3번 5칸)
#                    (event_id는 "event" 서랍에 이미 있어서 여기서는 뺐다)
#   바깥 칸        : ticket_id, status, action_result, message, updated_at
#
# 팀 표준 글자
#   상태 : 신규 / 승인대기 / 조치중 / 완료 / 실패 / 모니터링
#   조치 결과 : success / fail / skipped / approval_required
#
# 주석 표시 약속
#   [뭐함] 이 줄(덩어리)이 하는 일   [출처] 값이 어디서 오는지
#   [흐름] 실제 값을 넣으면 어떻게 돌아가는지   [왜] 왜 필요한지
# =====================================================================


# ---------------------------------------------------------------------
# 1. make_ticket : 티켓 1장 만들기
# ---------------------------------------------------------------------
def make_ticket(event, request, status):
    # [뭐함] 이벤트 1건과 그 조치 요청, 처음 상태로 티켓 서랍장 한 장을 만들어 돌려준다.
    # [출처] event   : def 괄호. 공통로그 2번의 이벤트 1건. (11칸이 모두 들어 있어야 한다)
    #        request : def 괄호. 공통로그 3번의 조치 요청 1건. (run_playbook이 돌려준 것)
    #        status  : def 괄호. playbook.py의 statuses[event_id] 값. 예) "조치중", "승인대기"
    # [왜]   status를 이 함수 안에서 정하지 않고 괄호로 받는 이유:
    #        상태를 정하는 곳을 playbook.py 한 군데로 두기 위해서다.
    #        여기서 또 정하면 두 파일의 상태가 어긋날 수 있다.
    # [주의] 모니터링만이면 run_playbook이 request로 None을 돌려준다.
    #        이 함수는 None을 받으면 request["action"]에서 에러가 난다.
    #        그래서 main.py에서 request가 None이 아닐 때만 이 함수를 불러야 한다.
    # [흐름] event_id가 "EVT-001"이면 ticket_id는 "TKT-EVT-001"이 된다.

    ticket_id = "TKT-" + event["event_id"]     # [뭐함] 글자 "TKT-" 뒤에 이벤트 번호를 붙여 티켓 번호를 만든다

    ticket = {
        "event": {                                          # 이벤트 정보 서랍 (공통로그 2번 11칸)
            "event_id": event["event_id"],                  # [출처] event 서랍장의 같은 이름 칸
            "event_type": event["event_type"],
            "user": event["user"],
            "src_ip": event["src_ip"],
            "risk_score": event["risk_score"],
            "priority": event["priority"],
            "asset": event["asset"],
            "impact_scope": event["impact_scope"],          # [주의] 철자 impact_scope (impct, imapct 아님)
            "detected_at": event["detected_at"],
            "rule": event["rule"],                          # 리포트의 "탐지 근거"에 쓴다
            "evidence": event["evidence"]                   # 리포트의 "탐지 근거"에 쓴다
                                                            # [주의] 공통로그 2번 카드에서 evidence는 글자가 아니라 "목록"이다.
                                                            #        예: ["2026-11-02 02:10:11", "2026-11-02 02:14:05"]
                                                            #        여기서는 목록을 그대로 옮기기만 한다. 글자로 바꾸는 일은 report.py가 한다.
        },
        "request": {                                        # 조치 요청 서랍 (공통로그 3번 5칸)
            "action": request["action"],                    # [출처] request 서랍장의 같은 이름 칸
            "target": request["target"],
            "response_level": request["response_level"],
            "reason": request["reason"],
            "dry_run": request["dry_run"]
        },
        "ticket_id": ticket_id,                             # [출처] 위에서 만든 변수
        "status": status,                                   # [출처] def 괄호로 받은 상태 글자
        "action_result": None,                              # 조치 결과 글자. 결과가 오기 전이라 None. update_ticket이 채운다
        "message": None,                                    # 조치 결과 설명 글자. update_ticket이 채운다
        "updated_at": event["detected_at"]                  # 처음에는 탐지 시각. update_ticket이 결과 시각으로 바꾼다
    }

    return(ticket)                                          # [주의] 돌려주는 줄이 없으면 호출한 쪽에는 None이 간다


# ---------------------------------------------------------------------
# 2. update_ticket : 조치 결과로 티켓 갱신하기
# ---------------------------------------------------------------------
def update_ticket(ticket, result):
    # [뭐함] 조치 결과(공통로그 5번)를 받아 티켓의 결과 칸, 설명 칸, 시각 칸, 상태 칸을 바꾼다.
    # [출처] ticket : def 괄호. make_ticket이 만든 티켓 서랍장.
    #        result : def 괄호. 1·3파트가 돌려준 조치 결과 1건. 쓰는 칸은 result, message, timestamp 셋.
    # [왜]   조치 결과 글자(result["result"])에 따라 상태를 다르게 정한다.
    # [팀이 정할 것] 강의 자료는 "조치가 성공했다고 티켓을 자동으로 닫지 말라"고 한다.
    #        지금 코드는 success이면 "완료"로 바꾼다. 팀 표준 상태 글자 6개에
    #        "사람이 확인하는 단계"가 없어서 이렇게 정했다. 팀이 다르게 정하면 이 줄만 고친다.
    # [규칙] success           -> "완료"
    #        fail              -> "실패"
    #        approval_required -> "승인대기"
    #        skipped           -> 상태는 그대로 두고 결과·설명·시각만 적는다.
    # [흐름] result["result"]가 "success"이고 timestamp가 "2026-11-02 02:15:05"이면
    #        action_result="success", updated_at="2026-11-02 02:15:05", status="완료"

    ticket["action_result"] = result["result"]       # [뭐함] 결과 글자를 티켓에 적는다
    ticket["message"] = result["message"]            # [뭐함] 결과 설명 글자를 티켓에 적는다
    ticket["updated_at"] = result["timestamp"]       # [뭐함] 갱신 시각을 결과가 만들어진 시각으로 바꾼다

    if result["result"] == "success":                # [뭐함] 결과 글자에 따라 상태를 정한다
        ticket["status"] = "완료"
    elif result["result"] == "fail":
        ticket["status"] = "실패"
    elif result["result"] == "approval_required":
        ticket["status"] = "승인대기"
    else:
        None                                         # [뭐함] skipped 등 나머지는 상태를 건드리지 않는다
                                                     #        (이 줄은 아무 일도 하지 않는다. 지워도 결과는 같다)

    return(ticket)                                   # [뭐함] 갱신된 티켓을 돌려준다


# ---------------------------------------------------------------------
# 3. make_alert_request : 알림 요청 만들기 (공통로그 4번)
# ---------------------------------------------------------------------
def make_alert_request(event, level, message):
    # [뭐함] 담당자에게 알림을 보내 달라는 요청 서랍장(4칸)을 만들어 돌려준다.
    # [출처] event   : def 괄호. 이벤트 1건. 여기서는 event_id 칸만 쓴다.
    #        level   : def 괄호. 알림 단계 숫자. 1이면 1차(보안 담당자), 그 외(2)는 2차(보안팀장).
    #        message : def 괄호. 알림에 쓸 글자.
    #        세 값은 모두 6번 main.py가 정해서 넘긴다. 누가 이 함수를 부를지는 팀이 정해야 한다.
    # [왜]   담당자에게 알리는 일은 1파트가 실행한다. 4파트는 "누구에게 무슨 말을"만 요청으로 만든다.
    # [칸] event_id, level, to, message   (공통로그 4번 카드의 칸 4개)
    # [흐름] level이 1이면 to는 "보안 담당자", 2면 "보안팀장"

    if level == 1:                                   # [뭐함] 1차 알림이면
        to = "보안 담당자"                            # [출처] 공통로그 4번 그림 예시의 to 값
    else:                                            # [뭐함] 아니면 (2차 알림)
        to = "보안팀장"                               # [출처] 강의 자료의 2차 담당자

    request = {
        "event_id": event["event_id"],               # [출처] event 서랍장의 event_id 칸
        "level": level,                              # [출처] def 괄호로 받은 숫자
        "to": to,                                    # [출처] 바로 위 if/else에서 정한 변수
        "message": message                           # [출처] def 괄호로 받은 글자
    }
    return(request)

실제로 한 실수 (다시 하지 않기)

make_ticket

  • request["response_level"] = status : status라는 이름이 없어서 NameError. 그리고 요청의 값을 덮어쓰고 있었다. → status를 def 괄호로 받는다.
  • status를 if 안에서만 만들고 else에서는 안 만들어서 UnboundLocalError. → 괄호로 받으면 사라지는 문제.
  • 서랍장을 [ ]로 시작함 : 서랍장은 { }다. [ ]는 목록이다.
  • "impact_scope": event["imapct_scope"] : 철자 오타로 KeyError. 칸 이름은 한 글자씩 맞춘다.
  • detected_at 칸이 없었다 : 이 칸이 있어야 updated_at의 처음 값을 정할 수 있다.
  • return만 쓰고 값이 없음 : 티켓이 호출한 쪽에 안 간다. → return(ticket)
  • 이름표에 따옴표 없음 : 변수로 읽힌다. → "ticket_id"
  • "updated_at": "detected_at" : 글자 그대로 들어간다. → event["detected_at"]
  • 칸 이름 update_at : 팀이 쓰는 이름은 updated_at이다.
  • ticket_id, status, 처럼 이름표 없이 값만 씀 : SyntaxError. → "ticket_id": ticket_id,
  • rule, evidence 칸을 처음에 안 넣음 : 5번 리포트의 "탐지 근거"를 만들 수 없다. → 추가했다.

update_ticket

  • 이 함수는 처음 쓴 그대로 맞았다. 4가지 결과를 모두 실행해서 확인했다.

make_alert_request

  • if level == 1: 아래에 "보안 담당자"만 쓰고 to =를 안 씀 : 글자를 적기만 하고 이름에 담지 않았다. 아래 "to": to가 이름을 못 찾는다. → to = "보안 담당자"
  • 서랍장 첫 칸 끝에 쉼표 빠짐 : 아래 줄이 전부 에러로 표시된다. 에러가 여러 개 떠도 원인은 쉼표 하나일 수 있다.
  • return을 안 씀 : 만들기만 하고 돌려주지 않았다.

초동 대응 리포트를 만든다. 리포트는 5부분이다. (강의 자료의 구성요소)

  • 사고 개요 : ticket["event"]의 event_id, event_type, user, src_ip, asset, impact_scope, priority, risk_score
  • 탐지 근거 : ticket["event"]의 rule, evidence, detected_at
  • 조치 내역 : ticket["request"]의 action, target, response_level + 조치 이력 파일의 같은 이벤트 줄 + 티켓의 action_result
  • 현재 상태 : ticket["status"]
  • 후속 조치 : 상태별 문장. 팀 기준이 아직 없다. (공통로그 카드 8장에 없었다)

함수 3개

  • read_log(filename) : 조치 이력 파일 읽기. 완료.
  • make_report(ticket, logs) : 리포트 줄 목록 만들기. 후속 조치만 빼고 완료.
  • save_report(lines, filename) : 줄 목록을 json 파일로 저장. 완료.

받아 오는 것

  • ticket : 6번 main.py가 4번 make_ticket이 돌려준 티켓을 넣어 준다.
  • logs : 6번 main.py가 read_log가 돌려준 목록을 넣어 준다.
  • 테스트에서는 main.py 대신 테스트 코드가 make_ticket을 불러 티켓을 만든다. 이유 : 티켓은 어디에도 저장되지 않아서, 이 파일을 실행할 때마다 새로 만들어야 한다.

출력 칸마다 "어디서 오나?" (2단계 연습)

리포트 한 줄씩 값이 어디서 오는지 물었다.

  • 사고 개요 8줄 : 티켓 안 "event" 서랍 (ticket["event"]["칸이름"])
  • 탐지 근거 3줄 : 같은 "event" 서랍
  • 조치 3줄 : 티켓 안 "request" 서랍 (ticket["request"]["칸이름"])
  • 이력 3줄 : logs 목록 안의 기록. 그런데 이 파일에는 여러 이벤트의 기록이 섞여 있어서 이벤트 번호가 같은 것만 고른다.
  • 결과 1줄 : 티켓의 action_result. 결과가 오기 전에는 None이라서 None인지 먼저 본다.
  • 상태 1줄 : 티켓의 status

값의 모양을 먼저 본다 (이번에 제일 크게 배운 것)

글자 뒤에 +로 붙이기 전에 공통로그 카드에서 그 값의 모양을 본다.

  • 따옴표로 싸여 있으면 글자 → 그대로 붙인다. 예 "emp3"
  • 따옴표 없는 숫자 → str( )로 감싼다. 예 90은 str(90) → "90"
  • 대괄호 [ ]로 싸여 있으면 목록 → ", ".join(목록)으로 글자 하나로 만든다. 예 ["A", "B"]는 "A, B"
  • None이 올 수 있는 값 → if 값 is None:으로 먼저 본다

이 규칙을 안 지켜서 이번에 TypeError 3가지가 났다. 아래 실제로 한 실수 (report.py) ↗에 있다.

문제 문장 → 코드 모양

  • "한 줄을 리포트에 더한다" → lines.append("글자:" + 값) (한 번에 한 줄)
  • "목록 안의 기록을 하나씩 본다" → for log in logs:
  • "이 이벤트 것만 고른다" → if log["event_id"] == ticket["event"]["event_id"]:
  • "결과가 아직 없으면 '결과 없음', 있으면 그 값" → if ticket["action_result"] is None: ... else: ...
  • "줄들을 돌려준다" → return (lines)

# =====================================================================
# report.py  (4파트 대응·리포트 - 5번 파일)   << 만드는 중: 함수 3개 완료, 후속 조치 줄만 예정 >>
#
# 이 파일이 하는 일
#   초동 대응 리포트를 만든다. 리포트는 5부분이다. (강의 자료의 초동 대응 리포트 구성요소)
#     1. 사고 개요   2. 탐지 근거   3. 조치 내역   4. 현재 상태   5. 후속 조치
#   함수 계획
#     read_log(filename)         : containment_log.json을 읽어 조치 이력을 돌려준다.        [완료]

#                                  1~4번 부분은 [완료], 5번 후속 조치 부분은 [예정]
#     save_report(lines, filename): 리포트 줄 목록을 json 파일로 저장한다.                   [완료]
#
# 이 파일이 "받아 오는 것" (값의 출처)
#   containment_log.json : 1·3파트가 만든 조치 이력 파일 (공통로그 6번).
#                          칸 7개: timestamp, event_id, action, target, reason, result, dry_run
#                          공통로그 6번 설명: "파트4는 이 파일을 읽어 리포트의 '조치 내역'을 채워요."
#                          [확인 필요] 카드에는 기록 1건 모양만 있다. 이 파일이 기록 여러 건의
#                          목록 [ {...}, {...} ] 인지는 1·3파트에 물어봐야 한다.
#   ticket               : 4번 ticket.py의 make_ticket이 만든 티켓. 6번 main.py가 넘겨 준다.
#                          안에 "event"(11칸), "request"(5칸), ticket_id, status, action_result, message, updated_at
#
# 이 파일이 "내보내는 것"
#   make_report(...) -> 글자(줄)들이 든 목록. 한 줄이 글자 하나다.
#
# 파일 이름이 다르거나 모양이 다르면 : 5_상황별_고치기 문서를 본다.
#
# 주석 표시 약속
#   [뭐함] 이 줄(덩어리)이 하는 일   [출처] 값이 어디서 오는지   [왜] 왜 필요한지
#   [흐름] 실제 값을 넣으면 어떻게 돌아가는지
# =====================================================================

import json     # [뭐함] json 파일을 읽고(json.load) 쓰는(json.dump) 도구를 가져온다.


# ---------------------------------------------------------------------
# 1. read_log : containment_log.json 읽기
# ---------------------------------------------------------------------
def read_log(filename):
    # [뭐함] 파일 이름 글자를 받아, 그 파일 안의 조치 이력 목록을 돌려준다.
    # [출처] filename : def 괄호. 6번 main.py가 "containment_log.json"을 넣어 준다.
    # [흐름] filename이 "containment_log.json"이면 파일 안의 [ {...}, {...} ] 목록이 logs에 담겨 돌아온다.

    with open(filename, "r", encoding="utf-8") as file:   # [뭐함] 읽기("r")로 열고 file이라고 부른다
                                                          # [왜] encoding="utf-8"이 없으면 윈도우에서
                                                          #      한글이 든 파일을 읽다가 에러가 날 수 있다.
        logs = json.load(file)                            # [뭐함] 파일 안의 글자를 파이썬 목록으로 바꿔 logs에 담는다
    return (logs)                                         # [주의] with와 같은 칸(4칸)에 쓴다. with 밖에서 돌려준다.


# ---------------------------------------------------------------------
# 2. make_report : 티켓 1장 + 조치 이력 -> 리포트 줄 목록
# ---------------------------------------------------------------------
def make_report(ticket, logs):
    # [뭐함] 티켓과 조치 이력을 받아, 리포트의 줄들을 목록(lines)에 차례로 담아 돌려준다.
    # [출처] ticket : def 괄호. main.py가 4번 make_ticket(또는 update_ticket)이 돌려준 티켓을 넣어 준다.
    #        logs   : def 괄호. main.py가 위 read_log가 돌려준 목록을 넣어 준다.
    # [왜]   한 줄을 더할 때마다 lines.append( 글자 하나 ) 를 한 번 쓴다.
    #        append는 재료를 1개만 받는다. 쉼표로 여러 개를 넣으면 TypeError가 난다.
    # [생각법] 값을 글자 뒤에 + 로 붙이기 전에 카드에서 그 값의 모양을 본다.
    #          글자면 그대로, 숫자면 str( ), 목록이면 ", ".join( ).
    lines = []                                  # [뭐함] 빈 목록을 만든다. 아래에서 줄을 하나씩 더한다.

    # ===== 사고 개요 (티켓의 "event" 서랍, 공통로그 2번 칸) =====
    lines.append("이벤트 ID:" + ticket["event"]["event_id"])        # 예: "이벤트 ID:EVT-001"
    lines.append("유형:" + ticket["event"]["event_type"])           # 예: ABNORMAL_LOGIN
    lines.append("사용자:" + ticket["event"]["user"])               # 예: emp3
    lines.append("IP:" + ticket["event"]["src_ip"])                 # 예: 192.168.30.12
    lines.append("자산:" + ticket["event"]["asset"])                # 예: occ
    lines.append("영향 범위:" + ticket["event"]["impact_scope"])    # 예: single_user
    lines.append("우선순위:" + ticket["event"]["priority"])         # 예: HIGH
    lines.append("위험 점수:" + str(ticket["event"]["risk_score"])) # [주의] risk_score는 숫자(90).
                                                                    #       글자 + 숫자는 TypeError라서 str( )로 감싼다.

    # ===== 탐지 근거 (티켓의 "event" 서랍) =====
    lines.append("탐지 규칙:" + ticket["event"]["rule"])
    lines.append("근거:" + ", ".join(ticket["event"]["evidence"]))
                                                # [왜] 카드 2번에서 evidence는 글자가 아니라 시각 글자들의 "목록"이다.
                                                #      ", ".join(목록)은 글자들 사이에 ", "를 넣어 글자 하나로 만든다.
                                                # [흐름] ["A", "B"] -> "A, B" -> "근거:A, B"
    lines.append("탐지 시각:" + ticket["event"]["detected_at"])

    # ===== 조치 내역 (1) : 티켓의 "request" 서랍, 공통로그 3번 칸 =====
    # [주의] 이 3줄은 티켓에서 꺼내는 것이라 for 안에 넣지 않는다.
    #        for 안에 넣으면 이력 개수만큼 반복되고, 이력이 없으면 한 줄도 안 나온다.
    lines.append("조치:" + ticket["request"]["action"])             # 예: block_ip
    lines.append("대상:" + ticket["request"]["target"])             # 예: 192.168.30.12
    lines.append("대응 등급:" + ticket["request"]["response_level"])# 예: 즉시 자동조치

    # ===== 조치 내역 (2) : 조치 이력 파일에서 이 이벤트의 줄만 골라 더한다 =====
    # [뭐함] logs 목록에서 기록을 하나씩 꺼내 log라고 부르고, 이벤트 번호가 같을 때만 3줄을 더한다.
    # [출처] log는 for가 만든 이름이다. 기록 한 건이 들어 있다. 칸은 공통로그 6번 칸.
    # [흐름] logs가 [] 이면 for가 한 번도 안 돌아서 이력 3줄이 빠진다. 에러는 나지 않는다.
    for log in logs:
        if log["event_id"] == ticket["event"]["event_id"]:
            lines.append("이력 시각:" + log["timestamp"])
            lines.append("이력 결과:" + log["result"])
            lines.append("이력 사유:" + log["reason"])

    # ===== 조치 내역 (3) : 티켓에 적힌 결과 =====
    # [왜] action_result는 조치 결과가 오기 전에는 None 이다. None은 글자가 아니라서
    #      "글자" + None 은 TypeError가 난다. 그래서 None인지 먼저 본다.
    if ticket["action_result"] is None:
        lines.append("조치 결과:결과 없음")
    else:
        lines.append("조치 결과:" + ticket["action_result"])

    # ===== 현재 상태 =====
    # [주의] 이 줄은 if/else 바깥(4칸)에 쓴다. else 안(8칸)에 쓰면 결과가 있을 때만 나온다.
    lines.append("현재 상태:" + ticket["status"])

    # ===== 후속 조치 =====
    # [예정] 상태별로 어떤 문장을 넣을지는 팀 기준을 기다린다. (공통로그 카드 8장에 규칙이 없었다)
    #        임시 규칙 4줄은 Claude가 만든 것이고 팀이 확정한 것이 아니다.

    # [나중에 쓸 틀] 지금은 주석이라 돌지 않는다. 쓰고 싶을 때 아래 8줄의 맨 앞 "# "를 지운다.
    #   - 규칙 4개 = 승인대기, 실패, 완료, 그 외. 줄은 8줄이다. (if/elif/elif/else 가 각각 append 1줄을 가진다)
    #   - 쓰면 줄 수가 19 -> 20 이 된다. (경우 3은 16 -> 17)
    #   - 문장이 바뀌면 따옴표 안 글자만 고친다. 상태가 늘면 elif 2줄을 더한다.
    #   - 팀이 LLM으로 정하면 8줄을 지우고 함수를 부르는 줄 하나로 바꾼다.
    #   - [주의] 8줄은 if/else 바깥(4칸)에, 현재 상태 줄 아래에, return 위에 쓴다.
    #   - [출처] ticket["status"]는 4번 ticket.py가 넣은 상태 글자다. 팀 표준 : 신규/승인대기/조치중/완료/실패/모니터링
    #   - [임시 규칙] 이 4줄 규칙은 Claude가 만든 임시 규칙이고 팀이 확정한 것이 아니다.
    #
    # if ticket["status"] == "승인대기":
    #     lines.append("후속 조치:보안 담당자 승인 필요")
    # elif ticket["status"] == "실패":
    #     lines.append("후속 조치:수동 조치 필요, 보안팀장에게 보고")
    # elif ticket["status"] == "완료":
    #     lines.append("후속 조치:상황 재확인 후 종결 여부 검토")
    # else:
    #     lines.append("후속 조치:경과 관찰")

    return (lines)                              # [주의] 맨 아래, 4칸. 한 번만 쓴다.


# ---------------------------------------------------------------------
# 3. save_report : 리포트 줄 목록 -> 파일로 저장
# ---------------------------------------------------------------------
def save_report(lines, filename):
    # [뭐함] 줄 목록(lines)을 filename 파일에 저장한다.
    # [출처] lines    : def 괄호. make_report가 돌려준 줄 목록. 예: ["이벤트 ID:EVT-001", ... 19개]
    #        filename : def 괄호. main.py가 정한다. 예: "report_EVT-001.json"
    # [왜 json.dump] 3번 false_positive.py의 save_feedback에서 배운 그 줄이다.
    #        json.dump는 목록 전체를 한 번에 파일에 적는다. for가 필요 없다.
    #        (글자 모양 그대로 보고 싶으면 for line in lines: file.write(line + "\n") 도 된다.
    #         대신 file.write(lines)처럼 목록을 통째로 넣으면 TypeError가 난다.)
    # [흐름] 파일 안은 [ "이벤트 ID:EVT-001", "유형:ABNORMAL_LOGIN", ... ] 모양이 된다.
    with open(filename, "w", encoding="utf-8") as file:   # [뭐함] 쓰기("w")로 연다
                                                          # [왜] encoding="utf-8"이 없으면 윈도우가
                                                          #      한글을 다른 방식으로 저장해, 나중에 읽을 때 에러가 난다.
        json.dump(lines, file, ensure_ascii=False, indent=4)
        # lines              : 적을 것
        # file               : 적을 곳
        # ensure_ascii=False : 한글을 \uXXXX 기호로 바꾸지 않고 그대로 적는다
        # indent=4           : 줄마다 4칸 띄워 읽기 좋게 한다

왜 이 순서인가 (제일 중요)

코드는 위에서 아래로 한 줄씩 실행된다. 앞 줄이 만든 값을 뒤 줄이 쓴다. 그래서 순서가 곧 의미다.

  • 3단계의 run_playbook이 statuses를 채워야, 바로 아래 make_ticket에 statuses[event_id]를 넣을 수 있다.
  • 3단계의 make_ticket이 tickets를 채워야, 4단계 tickets["EVT-001"]과 5단계 for event_id in tickets:가 쓸 수 있다.
  • 4단계가 5단계보다 먼저여야 한다. 아래 두 경우를 EVT-001 실제 값으로 본다.

4단계가 먼저일 때 (맞는 순서)

  • 4단계에서 update_ticket이 EVT-001 티켓의 action_result를 None에서 "success"로, status를 "조치중"에서 "완료"로 바꾼다.
  • 5단계에서 make_report가 그 티켓을 읽는다. 조치 결과:success, 현재 상태:완료가 파일에 저장된다.

5단계가 먼저일 때 (틀린 순서)

  • 5단계에서 make_report가 읽을 때 티켓의 action_result는 아직 None이다. 조치 결과:결과 없음, 현재 상태:조치중이 파일에 저장된다.
  • 그 뒤 4단계가 티켓을 바꿔도 이미 저장한 파일은 안 바뀐다.
  • 에러는 나지 않는다. 그래서 맨 아래 확인 코드가 필요하다. 실제로 이 순서로 실행하면 EVT-001 저장 내용 같은가: False가 나온다.

줄마다 "어디서 오나?"

함수를 부르는 줄마다 괄호 안 이름이 4곳(곳 1 def 괄호 / 곳 2 위에서 이름 =으로 만듦 / 곳 3 서랍장에서 꺼냄 / 곳 4 import) 중 어디서 왔는지 적는다. 괄호 안 순서는 그 함수의 def 줄 순서와 같게 한다.

  • run_playbook(event, vip_data, statuses) : def 줄은 (event, vip_data, statuses)
    • event : 곳 2. 바로 위 for event in detections:가 만든 이름. 이벤트 1건.
    • vip_data : 곳 2. 1단계에서 vip_data = json.load(file)로 만든 이름.
    • statuses : 곳 2. 2단계에서 statuses = {}로 만든 이름.
  • make_ticket(event, request, statuses[event_id]) : def 줄은 (event, request, status)
    • request : 곳 2. 바로 위 줄 request = run_playbook(...)이 만든 이름.
    • statuses[event_id] : 곳 3. statuses 서랍장에서 이 이벤트 번호 이름표로 꺼낸 글자 하나. 예 "조치중". 서랍장 전체를 넣지 않는다.
    • event_id : 곳 2. 바로 위 줄 event_id = event["event_id"]이 만든 이름.
  • apply_result(statuses, result) : def 줄은 (statuses, result)
    • result : 곳 2. 4단계 맨 위 result = {...}. 칸 이름 7개는 공통로그 5번 카드, 값은 내가 정한 테스트 값.
    • tickets를 넣으면 안 된다. 이 함수는 result["event_id"]로 상태 칸을 찾는다. tickets에는 "event_id" 이름표가 없어서 KeyError: 'event_id'가 난다.
  • update_ticket(tickets["EVT-001"], result) : def 줄은 (ticket, result)
    • tickets["EVT-001"] : 곳 3. tickets 서랍장에서 "EVT-001" 이름표로 꺼낸 티켓 1장.
    • 따옴표 안은 이벤트 번호 글자다. "event_id"라고 쓰면 그 글자가 이름표가 되어 KeyError가 난다.
  • make_report(tickets[event_id], logs) : def 줄은 (ticket, logs)
    • event_id : 곳 2. 바로 위 for event_id in tickets:가 만든 이름. tickets 서랍장의 이름표("EVT-001" 같은 글자)를 하나씩 꺼낸다.
    • logs : 곳 2. 1단계 logs = read_log(...).
  • save_report(lines, "report_" + event_id + ".json") : def 줄은 (lines, filename)
    • lines : 곳 2. 바로 위 줄 lines = make_report(...).
    • 파일 이름 : 글자 "report_" + 이름 event_id + 글자 ".json"을 +로 이은 글자. 이벤트마다 이름이 달라서 서로 덮어쓰지 않는다.

#     -> 조치 결과 반영(상태, 티켓) -> 티켓마다 리포트 만들어 저장
#     -> 오탐 입력 파일에 적힌 이벤트마다 오탐 처리(복구 요청 만들기 + 오탐 기록 저장)
#
# 이 파일을 실행하면 (같은 폴더에 아래 파일이 있어야 한다)
#   읽는 파일   : detections.json (2파트), vip_accounts.json, containment_log.json (1·3파트),
#                 false_positive_input.json (오탐으로 확인한 이벤트 목록. 사람이 적는다)
#   만드는 파일 : report_EVT-001.json 처럼 티켓이 있는 이벤트마다 1개,
#                 false_positive_feedback.json (오탐 기록. 3번 파일이 쓴다)
#   화면 출력   : 맨 아래 확인 코드(if __name__ == "__main__": 안)의 출력만 나온다
#
# 이 파일이 "가져오는 것" (값의 출처)
#   playbook.py : run_playbook (이벤트 1건 -> 조치 요청 또는 None, 상태 적기), apply_result (결과 -> 상태 바꾸기)
#   ticket.py   : make_ticket (티켓 만들기), update_ticket (결과로 티켓 바꾸기)
#   report.py   : read_log (조치 이력 읽기), make_report (리포트 줄 만들기), save_report (파일 저장)
#   false_positive.py : read_false_positive_input (오탐 입력 파일 읽기), handle_false_positive (복구 요청 만들기 + 오탐 기록)
#   classifier.py는 playbook.py가 안에서 부르므로 여기서 가져오지 않는다.
#
# 이 파일에서 제일 중요한 것 : 순서
#   조치 결과를 반영하는 4번 단계(apply_result, update_ticket)가
#   리포트를 만들고 저장하는 5번 단계보다 먼저여야 한다.
#   순서가 바뀌면 저장된 리포트에 "조치 결과:결과 없음", "현재 상태:조치중"이 남는다.
#   (실제로 겪었다. 3_작업기록 문서의 고친 것 참고)
#
# 아직 이 파일에 없는 것 (팀이 정하거나 대영이 다음에 붙인다)
#   - make_alert_request (누가 부를지 팀이 정해야 한다)
#   - 조치 결과 4번 단계는 지금 가짜 결과다. 진짜는 1·3파트가 돌려준 값을 넣는다.
#   - 5-2단계(오탐 처리)가 만든 복구 요청은 지금 화면에 찍기만 한다. 1·3파트에 넘기는 줄은 아직 없다.
#   - 5-2단계의 result는 EVT-001의 가짜 결과 하나뿐이다. 다른 이벤트 번호를 입력 파일에 적으면 맞지 않는 값이 들어간다.
#
# 주석 표시 약속
#   [뭐함] 이 줄(덩어리)이 하는 일   [출처] 값이 어디서 오는지
#   [흐름] 실제 값을 넣으면 어떻게 돌아가는지   [왜] 왜 필요한지
# =====================================================================

import json     # [뭐함] json 파일을 읽는 도구(json.load)를 가져온다.
                # [왜]   1단계에서 detections.json, vip_accounts.json을 이 파일이 직접 읽는다.
                #        이 줄이 없으면 NameError: name 'json' is not defined

from playbook import run_playbook, apply_result   # [출처] 2번 playbook.py의 함수 2개
from ticket import make_ticket, update_ticket      # [출처] 4번 ticket.py의 함수 2개
from report import read_log, make_report, save_report   # [출처] 5번 report.py의 함수 3개
from false_positive import handle_false_positive, read_false_positive_input   # [출처] 3번 false_positive.py의 함수 2개
# [주의] from 뒤에는 파일 이름에서 .py를 뺀 글자를 쓴다. (from playbook.py import ... 는 에러)
# [주의] 이 파일과 같은 폴더에 playbook.py, ticket.py, report.py, classifier.py, false_positive.py가 있어야 한다.


# ---------------------------------------------------------------------
# 1단계. 입력 파일 3개 읽기
# ---------------------------------------------------------------------
# [뭐함] 이벤트 목록과 VIP 명단을 읽는다.
# [왜]   classifier.py는 import 해도 파일을 읽지 않는다. 읽는 일은 이 main.py가 한다.
# [왜]   encoding="utf-8" : 한글이 든 json을 윈도우에서 읽을 때 생기는 UnicodeDecodeError(cp949)를 막는다.
with open("detections.json", "r", encoding="utf-8") as file:
    detections = json.load(file)      # [출처] 2파트가 만든 이벤트 목록(list). 한 칸이 이벤트 1건(서랍장).
                                      # [흐름] 샘플 파일이면 7칸짜리 목록, 대영 컴퓨터 파일이면 1칸짜리 목록

with open("vip_accounts.json", "r", encoding="utf-8") as file:   # 앞 with가 끝났으므로 file 이름을 다시 써도 된다
    vip_data = json.load(file)        # [출처] VIP 명단 서랍장(dict). {"vip_users": ["admin"], "vip_ips": []}
                                      # [주의] 이름을 vip_data로 한다. detections에 다시 담으면 이벤트 목록이 사라진다.

logs = read_log("containment_log.json")   # [출처] 5번 report.py의 read_log. 조치 이력 목록(list)을 돌려준다.
                                          # [왜] 3단계 리포트 만들기에서 쓴다. 한 번만 읽고 계속 쓴다.
# [주의] logs = ... 줄은 with 안(들여쓰기)이 아니라 맨 왼쪽(0칸)에 쓴다.


# ---------------------------------------------------------------------
# 2단계. 빈 서랍장 4개 만들기
# ---------------------------------------------------------------------
statuses = {}   # [뭐함] {이벤트번호: 상태 글자}. 빈 서랍장으로 시작한다.
                # [출처] 3단계의 run_playbook이 이벤트마다 칸을 채운다. apply_result가 칸을 바꾼다.
                # [흐름] 3단계가 끝나면 {"EVT-001": "조치중", "EVT-002": "승인대기", ...}
tickets = {}    # [뭐함] {이벤트번호: 티켓 서랍장}. 빈 서랍장으로 시작한다.
                # [출처] 3단계의 make_ticket이 조치 요청이 있는 이벤트만 칸을 채운다.
                # [흐름] 모니터링만인 이벤트는 칸이 없다.
requests = {}   # [뭐함] {이벤트번호: 조치 요청 서랍장}. 빈 서랍장으로 시작한다.
                # [출처] 3단계에서 run_playbook이 돌려준 request를 이벤트 번호 이름표로 넣는다.
                # [왜]   3단계의 request 이름은 for가 한 바퀴 돌 때마다 새 값으로 바뀐다.
                #        5-2단계(오탐 처리)가 이벤트별 요청을 꺼내 쓰려면 따로 보관해야 한다.
events = {}     # [뭐함] {이벤트번호: 이벤트 서랍장}. 빈 서랍장으로 시작한다.
                # [출처] 3단계에서 for가 꺼낸 event를 이벤트 번호 이름표로 넣는다.
                # [왜]   5-2단계(오탐 처리)가 이벤트 번호로 이벤트를 꺼내 쓰려면 필요하다.


# ---------------------------------------------------------------------
# 3단계. 이벤트를 하나씩 처리해서 티켓 만들기
# ---------------------------------------------------------------------
for event in detections:    # [뭐함] 이벤트 목록에서 1건씩 꺼내 event라고 부른다. (event는 서랍장 1개)
    request = run_playbook(event, vip_data, statuses)
    # [출처] 괄호 순서는 playbook.py의 def 줄 run_playbook(event, vip_data, statuses)와 같다.
    #        event    : 바로 위 for가 꺼낸 이벤트 1건
    #        vip_data : 1단계에서 읽은 VIP 명단
    #        statuses : 2단계에서 만든 서랍장. run_playbook이 이 이벤트의 처음 상태를 안에 적는다.
    # [돌려주는 것] 조치 요청 서랍장 6칸. 또는 None (모니터링만이거나, 모르는 이벤트 유형일 때)
    # [흐름] EVT-001(점수 90) -> statuses["EVT-001"]="조치중", request=6칸 서랍장
    #        EVT-004(점수 20) -> statuses["EVT-004"]="모니터링", request=None

    if request is not None:     # [뭐함] 조치 요청이 있을 때만 티켓을 만든다.
                                # [왜] make_ticket은 request["action"]을 읽는다. None을 넣으면 TypeError가 난다.
                                # [주의] None인지 볼 때는 == 대신 is not 을 쓴다.
        event_id = event["event_id"]    # [출처] 이벤트 서랍장의 "event_id" 칸. 예: "EVT-001"
        tickets[event_id] = make_ticket(event, request, statuses[event_id])
        # [뭐함] tickets 서랍장에 event_id 이름표로 티켓을 넣는다. (= 은 오른쪽을 먼저 계산한다)
        # [출처] make_ticket(event, request, status)의 def 순서와 같다.
        #        event   : for가 꺼낸 이벤트
        #        request : 바로 위 run_playbook이 돌려준 조치 요청
        #        status  : statuses[event_id]. run_playbook이 방금 적어 둔 처음 상태 글자.
        #                  (statuses 서랍장 전체가 아니라 이 이벤트 칸 하나를 꺼내 넣는다)
        # [주의] 서랍장에 넣을 때는 = 하나. (== 는 "같은가?" 비교라서 아무것도 넣지 않는다)
        requests[event_id] = request
        # [뭐함] requests 서랍장에 event_id 이름표로 조치 요청을 넣는다.
        # [출처] event_id는 바로 위 줄에서 만든 글자(예: "EVT-001"), request는 run_playbook이 돌려준 값.
        events[event_id] = event
        # [뭐함] events 서랍장에 event_id 이름표로 이벤트 1건을 넣는다.
        # [주의] 왼쪽은 서랍장 이름 events(s가 붙음), 오른쪽은 넣을 값 event(1건)다. 거꾸로 쓰면 에러 없이 events가 빈다.


# ---------------------------------------------------------------------
# 4단계. 조치 결과 반영하기 (리포트 만들기 전에 해야 한다)
# ---------------------------------------------------------------------
# [뭐함] 1·3파트가 조치를 실행하고 돌려준 결과(공통로그 5번 7칸)라고 가정한 가짜 결과다.
# [출처] 칸 이름 7개는 공통로그 5번 카드. 값은 내가 정한 테스트 값이다.
#        진짜 결과가 오면 이 서랍장을 1·3파트가 돌려준 값으로 바꾼다.
result = {
    "event_id": "EVT-001",
    "action": "block_ip",
    "target": "192.168.30.12",
    "result": "success",
    "message": "ok",
    "timestamp": "2026-11-02 02:15:05",
    "dry_run": False
}

apply_result(statuses, result)
# [뭐함] 결과를 보고 statuses 서랍장의 상태를 바꾼다. (돌려주는 값이 없다)
# [출처] apply_result(statuses, result)의 def 순서와 같다.
#        statuses : 2단계에서 만든 상태 서랍장
#        result   : 바로 위에서 만든 조치 결과 1건
#        tickets를 넣으면 안 된다. apply_result는 result["event_id"]로 statuses 칸을 찾는다.
#        tickets에는 "event_id" 이름표가 없어서 KeyError: 'event_id'가 난다.
# [흐름] result["result"]가 "success" -> statuses["EVT-001"]이 "조치중"에서 "완료"로 바뀐다.

update_ticket(tickets["EVT-001"], result)
# [뭐함] 같은 결과로 EVT-001 티켓의 결과 칸, 설명 칸, 시각 칸, 상태 칸을 바꾼다.
# [출처] update_ticket(ticket, result)의 def 순서와 같다.
#        ticket : tickets 서랍장에서 "EVT-001" 이름표로 꺼낸 티켓 1장. 따옴표를 빼고 event_id라고만 쓰면
#                 3단계의 마지막 event_id(마지막 이벤트 번호)가 들어가므로 이름표 글자를 직접 쓴다.
#        result : 위와 같은 조치 결과
# [흐름] action_result가 None에서 "success"로, status가 "완료"로, updated_at이 "2026-11-02 02:15:05"로 바뀐다.
# [주의] 서랍장 안의 티켓을 바로 바꾸는 함수라서 돌려준 값을 담지 않아도 tickets 안 티켓이 바뀐다.
# [주의] tickets에 "EVT-001" 칸이 없으면(EVT-001이 모니터링만이면) KeyError가 난다.


# ---------------------------------------------------------------------
# 5단계. 티켓마다 리포트 만들어 저장하기
# ---------------------------------------------------------------------
for event_id in tickets:    # [뭐함] tickets 서랍장에서 이름표(이벤트 번호)를 1개씩 꺼낸다.
                            # [주의] for는 서랍장에서 이름표를 꺼낸다. 티켓이 아니라 "EVT-001" 같은 글자다.
                            #        그래서 이름을 event_id로 지었다. (for event in event 로 쓰면 안 된다)
    lines = make_report(tickets[event_id], logs)
    # [출처] make_report(ticket, logs)의 def 순서와 같다.
    #        ticket : tickets[event_id]. 이 이벤트의 티켓 1장
    #        logs   : 1단계에서 읽은 조치 이력 목록
    # [돌려주는 것] 리포트 줄 목록(list). 한 줄이 글자 하나.
    save_report(lines, "report_" + event_id + ".json")
    # [출처] save_report(lines, filename)의 def 순서와 같다.
    #        lines    : 바로 위 리포트 줄 목록
    #        filename : 글자 "report_" + 이벤트 번호 + 글자 ".json". 예: "report_EVT-001.json"
    # [왜] 이벤트마다 파일 이름이 달라야 서로 덮어쓰지 않는다.
    # [흐름] tickets에 7건 중 6장이면 report_EVT-001.json ... 파일 6개가 생긴다.


# ---------------------------------------------------------------------
# 5-2단계. 오탐 처리하기
# ---------------------------------------------------------------------
# [뭐함] 사람이 "이건 오탐이다"라고 확인한 이벤트마다 복구 요청을 만들고 오탐 기록을 남긴다.
# [왜]   "오탐 대응(복구·기록)"이 4파트 할 일 6개 중 하나다. main.py가 이 함수를 부르지 않으면 합칠 때 오탐 기록이 안 만들어진다.
# [위치] 3단계가 requests, events를 다 채운 뒤, 4단계가 result를 만든 뒤여야 한다.
#        이 단계는 tickets, statuses를 바꾸지 않으므로 5단계(리포트 저장)의 앞이든 뒤든 저장 내용에 영향이 없다.

false_list = read_false_positive_input("false_positive_input.json")
# [출처] 3번 false_positive.py의 함수 6. 파일 이름 글자를 넣으면 목록(list)을 돌려준다. 파일이 없으면 [].
# [흐름] [{"event_id": "EVT-001", "reason": "정상 업무 로그인", "confirmed_by": "admin"}]

for item in false_list:     # [뭐함] 목록에서 1건씩 꺼내 item이라고 부른다. (item은 서랍장 1개)
    event_id = item["event_id"]     # [출처] item의 "event_id" 칸. 예: "EVT-001". 아래 두 서랍장을 여는 이름표다.
    restore = handle_false_positive(events[event_id], requests[event_id],
                                    result, item["reason"], item["confirmed_by"])
    # [출처] 괄호 순서는 false_positive.py의 def handle_false_positive(event, request, result, reason, confirmed_by)와 같다.
    #        event        : events[event_id]      (변수 event_id의 값이 이름표라서 따옴표가 없다)
    #        request      : requests[event_id]
    #        result       : 4단계에서 만든 조치 결과 (지금은 가짜 값)
    #        reason       : item["reason"]        (칸 이름 글자 그대로라서 따옴표가 있다)
    #        confirmed_by : item["confirmed_by"]
    # [돌려주는 것] 복구 요청 서랍장 6칸. 원래 조치가 success가 아니면 None. 오탐 기록은 항상 파일에 저장된다.
    # [흐름] EVT-001, result가 success -> restore = {"action": "unblock_ip", "reason": "false_positive", ...}
    print("복구 요청:", restore)
    # [왜] 복구 요청을 1·3파트에 넘기는 방법이 아직 안 정해졌다. 지금은 화면에 찍어서 확인만 한다.

# [참고] 이 확인 코드는 문서를 만들면서 더한 것이다.
if __name__ == "__main__":
    # ============================================================
    # 이 확인 코드가 하는 일
    #   위 1~5단계가 의도대로 됐는지 값을 찍어서 본다.

실제로 한 실수 (다시 하지 않기)

맨 위

  • from playbook.py import ... : .py를 뺀다. → from playbook import ...
  • import json 빠짐 : 파일을 읽으려면 필요하다.
  • VIP 명단을 detections = json.load(file)로 읽음 : 이벤트 목록이 든 이름에 덮어쓴다. → vip_data = json.load(file)
  • logs = ...을 with 안쪽 들여쓰기에 씀 : 맨 왼쪽(0칸)으로 옮긴다.
  • sstatuses : 철자 오타. → statuses

3단계

  • run_playbook(vip_data, detections, event) 같은 순서 : 순서는 def 줄 (event, vip_data, statuses)와 같게. 셋째 칸에는 이벤트 목록이 아니라 statuses.
  • tickets[...] == make_ticket(...) : ==는 "같은가?" 비교라 아무것도 넣지 않는다. → =
  • make_ticket(event, request, detections) : 셋째 칸은 상태 글자. → statuses[event_id]

5단계

  • for event_id in event: / make_report(event["event_id"], logs) : 꺼낼 곳은 tickets, 넣을 것은 티켓 1장. → for event_id in tickets:, make_report(tickets[event_id], logs)
  • "report_" + tickets + ".json" / "report_A" : 이벤트마다 이름이 달라야 한다. → "report_" + event_id + ".json"

4단계

  • apply_result(statuses, tickets) : 둘째 칸은 조치 결과. → apply_result(statuses, result)
  • update_ticket(tickets["event_id"], result) : 따옴표 안이 글자 그대로 이름표가 된다. → tickets["EVT-001"]
  • 4단계를 5단계 아래에 씀 : 에러 없이 저장 내용만 틀렸다(저장 내용 같은가: False). → 4단계를 for event_id in tickets: 위로 옮긴다.
  • 줄을 옮기다 # ==== 줄의 #가 지워짐 : SyntaxError. → #를 다시 붙인다.

5-2단계 오탐 처리 (2026-10-27 추가)

한눈에 : 사람이 오탐이라고 확인한 이벤트를 파일에 적어 두면, main.py가 그 파일을 읽어서 이벤트마다 복구 요청을 만들고 오탐 기록을 남긴다.

false_list = read_false_positive_input("false_positive_input.json")
for item in false_list:
    event_id = item["event_id"]
    restore = handle_false_positive(events[event_id], requests[event_id],
                                    result, item["reason"], item["confirmed_by"])
    print("복구 요청:", restore)

값이 어디서 오나 (변수 4개)

  • false_list : 파일을 읽은 목록을 담는 이름. 값 [{'event_id': 'EVT-001', 'reason': '정상 업무 로그인', 'confirmed_by': 'admin'}]. 이름이 없으면 다음 줄의 for가 목록을 쓸 수 없다.
  • item : for가 한 바퀴 돌 때 목록에서 꺼낸 1건. 값 {'event_id': 'EVT-001', 'reason': '정상 업무 로그인', 'confirmed_by': 'admin'}.
  • event_id : item["event_id"]를 꺼낸 글자 "EVT-001". events, requests 서랍장을 여는 이름표다.
  • restore : handle_false_positive가 돌려준 복구 요청. 값 {'event_id': 'EVT-001', 'action': 'unblock_ip', 'target': '192.168.30.12', ...}. request = run_playbook(...)처럼 돌려준 값을 이름에 담는다.

왜 requests, events 서랍장이 필요했나

  • handle_false_positive(event, request, result, reason, confirmed_by)는 재료 5개가 필요하다.
  • 오탐 입력 파일에서 바로 얻는 것은 reason, confirmed_by 둘뿐이다.
  • event, request는 이벤트 번호 "EVT-001"로 찾아야 한다. 3단계의 request는 for가 돌 때마다 새 값으로 바뀌어서 이벤트별로 남지 않는다. 그래서 requests, events 서랍장에 이벤트 번호 이름표로 따로 넣어 둔다.
  • 넣는 줄 : requests[event_id] = request, events[event_id] = event. 왼쪽이 서랍장 이름과 이름표, 오른쪽이 넣을 값이다.

따옴표 규칙

  • 칸 이름 글자 그대로 쓰면 따옴표를 붙인다 : item["reason"], item["confirmed_by"].
  • 변수의 값을 쓰면 따옴표를 뗀다 : events[event_id], requests[event_id].
  • 실행해서 확인한 것 : item[reason]은 NameError: name 'reason' is not defined, events["event_id"]는 KeyError: 'event_id'.

줄을 어디에 쓸지 정하는 3가지 질문

  • 1. 이 줄이 쓰는 이름은 어디서 만들어지나? (events, requests는 3단계 for가 끝나야 다 찬다. result는 4단계의 result = {...} 줄이 만든다.)
  • 2. 이 줄이 바꾸는 값을 읽는 줄은 어디 있나? (오탐 처리는 tickets, statuses를 안 바꾼다. 5단계 리포트 저장은 영향이 없다.)
  • 3. 재료를 다 만든 줄 아래, 바뀐 값을 읽는 줄 위에 쓴다. 그래서 5단계 아래, 테스트 블록 위에 썼다.

실제로 한 실수 (다시 하지 않기)

  • 함수 6 read_false_positive_input : if no filename: (no는 없는 말), open("filename", ...) (따옴표), json.load(file)를 담지 않음, return(file), return(filename).
  • event[event_id] = event : events의 s가 빠지면 에러 없이 events가 비어서 events 칸 수 0이 나온다.
  • event[event_id] = events : 왼쪽과 오른쪽이 거꾸로.

9. 에러가 났을 때▲ 맨 위

맨 아래 줄부터 읽는다. 아래가 이번에 실제로 났다.

  • TypeError: 'set' object is not subscriptable : 서랍장인 줄 알았던 것이 집합이다. { } 안이 "이름": 값이 아니거나 {...}처럼 점만 있다. 만든 줄을 본다.
  • NameError: name 'xxx' is not defined : 만든 적 없는 이름을 썼다. 위의 4곳 중 어디서도 안 왔다.
  • KeyError: 'xxx' : 서랍장에 그 이름표가 없다. 철자(imapct_scope)를 한 글자씩 맞춘다. 에러 줄 위에 print(서랍장.keys())를 넣어 실제 이름표를 본다.
  • UnboundLocalError : 이름을 if 안에서만 만들고, 안 걸린 경우에는 안 만들었다.
  • SyntaxError : 쉼표, 콜론, 괄호가 빠졌다. 에러가 여러 개 떠도 첫 번째 줄 하나가 원인일 때가 많다.
  • FileNotFoundError : 그 파일이 지금 폴더에 없다. 파일을 읽는 줄이 if __name__ == "__main__": 밖에 있는지 본다.
  • 빨간 물결 : VS Code가 보여 주는 에러 표시. 아래 Problems 숫자가 0이면 문법 에러는 없다.
  • ModuleNotFoundError: No module named 'playbook.py' : from playbook.py import ...처럼 .py를 붙였다. from playbook import ...
  • NameError: name 'json' is not defined : 맨 위에 import json이 없다.
  • KeyError: 'event_id' (apply_result 줄) : 두 번째 칸에 조치 결과 result가 아니라 tickets를 넣었다.
  • KeyError: 'EVT-001' (update_ticket 줄) : tickets에 그 이름표가 없다. 그 이벤트는 티켓을 만들지 않았다(모니터링만).
  • 에러가 없는데 저장된 리포트에 조치 결과:결과 없음 : 4단계(결과 반영)가 5단계(리포트 저장)보다 아래에 있다. 위로 옮긴다.
  • SyntaxError (줄을 옮긴 뒤) : 옮기다 # ==== 줄의 #가 지워졌다.
