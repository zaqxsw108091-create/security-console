0. 읽는 법▲ 맨 위

이 문서는 4파트(대응·리포트) 코드를 처음 보는 팀원을 위한 문서다.

대영의 설명 없이 읽고 자기 코드와 합칠 수 있게 썼다.

  • 코드를 바로 보고 싶으면 4. 바로 써 보기 ↗
  • 내 코드와 합치려면 9. main.py에 합치기 ↗와 11. 다른 사람 코드 확인법 ↗
  • 에러가 나면 13. 문제가 생기면 ↗
  • 확인 못 한 것은 14. 알아 둘 점 ↗

이 문서의 "왜 이렇게 만들었나"는 대영과 Claude가 정한 이유다. 팀이 정하지 않은 것은 "팀이 정해야 함"이라고 따로 적었다.

1. 프로젝트와 4파트▲ 맨 위

프로젝트는 "보안 대응 자동화"다. 파일과 JSON으로 주고받는다.

4파트 할 일 6가지

  • 대응 등급 분류
  • 플레이북과 이벤트 상태 관리
  • 승인 게이트 (자동, 승인, 보류)
  • 오탐 대응
  • 티켓 생성과 상태 갱신
  • 초동 대응 리포트

다른 파트와 만나는 곳은 공통로그 카드 7장이다. 7. 데이터 모양 ↗에 칸 이름을 적었다.

2. 왜 파이썬 파일이 6개인가▲ 맨 위

  • 1 classifier.py : 등급 정하기
  • 2 playbook.py : 상태와 조치 요청
  • 3 false_positive.py : 오탐
  • 4 ticket.py : 티켓과 알림 요청
  • 5 report.py : 리포트
  • 6 main.py : 위를 이어 붙임

이유는 할 일 6가지를 한 파일에 하나씩 맡기고, 이어 붙이는 일을 따로 두려는 것이다. 이 6개 구분은 Claude의 해석이다. 팀이 정한 것은 아니다.

한 파일에 다 넣지 않은 이유

  • 기준이 바뀌면 그 파일만 고친다. 예를 들어 등급 기준이 바뀌면 classifier.py만 고친다.
  • 파일마다 따로 실행해서 확인할 수 있다.

3. 파일 6개 소개▲ 맨 위

  • classifier.py : 이벤트 1건 → 등급 글자. 완료.
  • playbook.py : 등급 → 상태, 조치 요청 6칸. 조치 결과 → 상태. 완료.
  • false_positive.py : 오탐이면 복구 요청과 오탐 기록. 완료.
  • ticket.py : 티켓, 티켓 갱신, 알림 요청. 완료.
  • report.py : 리포트. read_log, make_report(후속 조치만 빼고) 완료.
  • main.py : 1~5번을 이어 붙인 파일. 1차 완료(오탐 처리 5-2단계까지. 알림 요청 줄은 아직 없다). 오탐 처리는 false_positive_input.json(오탐으로 확인한 이벤트 목록)을 읽는다. 파일 모양은 [{"event_id": "EVT-001", "reason": "정상 업무 로그인", "confirmed_by": "admin"}]이다. main_example.py는 1~4번만 이어 붙인 예시.

4. 바로 써 보기▲ 맨 위

같은 폴더에 아래 파일을 둔다.

  • classifier.py, playbook.py, false_positive.py, ticket.py, report.py, main.py, main_example.py
  • detections.json, vip_accounts.json, containment_log.json (샘플 파일을 따로 함께 보냈다)

순서

  • 파일마다 직접 실행(▶)해서 맨 아래 테스트 출력을 본다. 각 파일 맨 아래 if __name__ == "__main__": 안에 있다.
  • main.py를 실행하면 1~5번이 이어져 돈다. 티켓이 있는 이벤트마다 report_EVT-001.json 같은 파일이 생긴다. (main_example.py는 1~4번만 이어 붙인 예시)

기대하는 것

  • classifier.py : 이벤트마다 등급 글자가 한 줄씩 나온다.
  • playbook.py : 상태와 조치 요청이 나온다.
  • false_positive.py : 복구 요청, None, 기록 건수.
  • ticket.py : 상태 3개, 결과 4개, 알림 2개.
  • report.py : 경우 3개의 줄 수 19, 19, 16과 저장 확인 True.
  • main.py : 이벤트 수, 티켓 수, 6단계 확인: 완료 / 완료 / success / 2026-11-02 02:15:05, EVT-001 저장 내용 같은가: True. 샘플 파일(7건)이면 이벤트 수 7, 티켓 수 6.

이 폴더에서 실행하지 않고 다른 폴더에서 실행하면 FileNotFoundError가 난다. json 파일은 실행하는 폴더에 있어야 한다.

5. 만든 상황▲ 맨 위

  • 대영이 파이썬 초보라서, Claude가 뼈대를 주고 대영이 채우는 방식으로 만들었다.
  • 쓴 코드를 실행해 보고 틀린 곳을 알려 주고 고쳤다.
  • 상세는 3_작업기록 문서에 있다.
  • 시험 코드(맨 아래 __main__ 블록)는 Claude가 직접 줬다.

6. 폴더 준비▲ 맨 위

  • 모든 .py와 .json을 한 폴더에 둔다. from classifier import event_check가 같은 폴더의 파일을 찾기 때문이다.
  • 한글이 든 json을 쓰므로 파일을 여는 open(...)에는 모두 encoding="utf-8"을 넣었다. 예전에 encoding 없이 만든 false_positive_feedback.json이 폴더에 있으면 지우고 실행한다. 자세한 것은 5_상황별_고치기 문서 "한글이 깨질 때"에 있다.

7. 데이터 모양▲ 맨 위

공통로그 카드의 칸 이름이다. 다른 파트와 주고받는 값은 이 이름을 그대로 쓴다.

  • 이벤트 (2번 detections.json) : event_id, detected_at, rule, event_type, user, src_ip, risk_score, priority, asset, impact_scope, evidence

- 주의 : evidence는 글자가 아니라 시각 글자들의 목록이다. 예 ["2026-11-02 02:10:11", "2026-11-02 02:14:05"]. 글자 앞에 +로 바로 붙이면 TypeError가 난다. 한 줄로 이으려면 ", ".join(목록)을 쓴다.

  • 조치 요청 (3번) : event_id, action, target, response_level, reason, dry_run
  • 알림 요청 (4번) : event_id, level, to, message
  • 조치 결과 (5번) : event_id, action, target, result, message, timestamp, dry_run
  • 조치 이력 (6번 containment_log.json) : timestamp, event_id, action, target, reason, result, dry_run
  • 오탐 기록 (7번) : event_id, username, event_type, detected_as_anomaly, risk_score, is_actual_anomaly, false_positive_reason, confirmed_by, recorded_at

팀 표준 글자

  • 등급 : 즉시 자동조치, 승인 후 조치, 모니터링만
  • 상태 : 신규, 승인대기, 조치중, 완료, 실패, 모니터링
  • 조치 결과 : success, fail, skipped, approval_required
  • 조치 이름 : lock_account, unlock_account, terminate_session (1파트), block_ip, unblock_ip (3파트)
  • 이벤트 유형 : ABNORMAL_LOGIN, OFFHOUR_LOGIN, UNAUTHORIZED_ACCESS, MALICIOUS_IP, TRAFFIC_SPIKE, CORRELATED_ATTACK

공통로그 7번 예시는 이벤트 유형을 suspicious_login으로 적었다. 위 6개에 없는 글자다. 이 글자가 오면 choose_action이 None을 돌려준다.

8. 파일별 설명▲ 맨 위

classifier.py

  • 하는 일 : 점수로 등급을 정한다. 80 이상이면 즉시 자동조치, 50 이상이면 승인 후 조치, 그 외 모니터링만. 80 이상이어도 VIP면 승인 후 조치.
  • 받는 것 : user, src_ip, risk_score, rule (이벤트에서), vip_data (vip_accounts.json을 읽은 서랍장)
  • 돌려주는 것 : 등급 글자
  • 중요 : 파일 읽기는 __main__ 아래에서만 한다. import 해도 파일을 읽지 않는다.
  • 왜 level에 담고 마지막에 한 번만 return 하나 : 중간에 return 하면 VIP 검사가 실행되지 않는다.

playbook.py

  • 하는 일 : 상태를 statuses 서랍장에 적고, 조치 요청 6칸을 만든다.
  • 입구 : run_playbook(event, vip_data, statuses). 조치 요청 또는 None을 돌려준다. None이 오는 경우는 둘이다. 등급이 모니터링만이거나, 유형을 몰라서 action이 None일 때.
  • statuses : { event_id: 상태 글자 } 서랍장. main.py가 만들어 계속 넘긴다. 이 서랍장은 함수 안에서 바꾸면 바깥도 바뀐다.
  • apply_result(statuses, result) : 조치 결과를 받아 상태를 바꾼다. 돌려주는 값은 없다.
  • 조치 정하기 : ABNORMAL_LOGIN, TRAFFIC_SPIKE, CORRELATED_ATTACK, MALICIOUS_IP → block_ip / OFFHOUR_LOGIN → terminate_session / UNAUTHORIZED_ACCESS → lock_account
  • 이 매핑은 Claude가 정했고 팀 확정이 아니다. 바꾸려면 choose_action 한 곳만 고친다.

false_positive.py

  • 하는 일 : 오탐이면 복구 요청을 만들고 기록을 쌓는다.
  • 입구 : handle_false_positive(event, request, result, reason, confirmed_by) → 복구 요청 또는 None.
  • 복구하는 경우 : 조치가 success였고, dry_run이 아니고, 되돌릴 조치가 있을 때. 나머지는 None.
  • terminate_session은 되돌릴 방법이 없어 None이다.
  • 기록은 복구 여부와 상관없이 항상 쌓는다.
  • 기록 파일 : false_positive_feedback.json (공통로그 7번)

ticket.py

  • 하는 일 : 티켓 만들기, 조치 결과로 갱신, 알림 요청 만들기.
  • make_ticket(event, request, status) : 상태는 정하지 않고 받는다. request가 None이면 에러가 나므로 부르는 쪽에서 None이 아닐 때만 부른다.
  • 티켓 모양 : event 서랍(11칸), request 서랍(5칸), ticket_id, status, action_result, message, updated_at.
  • update_ticket(ticket, result) : success는 완료, fail은 실패, approval_required는 승인대기, skipped 등은 그대로.
  • make_alert_request(event, level, message) : level 1은 보안 담당자, 그 외는 보안팀장. 누가 부를지는 팀이 정해야 한다.

report.py (후속 조치만 남음)

  • read_log(filename) : containment_log.json을 읽어 목록으로 돌려준다.
  • make_report(ticket, logs) : 티켓 1장과 조치 이력으로 리포트 줄 목록을 만든다. 후속 조치만 아직 없다.

- 사고 개요, 탐지 근거는 티켓의 "event" 서랍에서, 조치는 "request" 서랍에서, 이력은 logs에서 같은 event_id인 것만 골라서 쓴다.

- evidence는 목록이라 ", ".join(...)으로 글자 하나로 만든다. risk_score는 숫자라 str( )로 감싼다.

  • save_report(lines, filename) : 줄 목록을 json.dump로 filename 파일에 저장한다(utf-8). 파일 이름은 .json으로 쓴다. 안은 [ "이벤트 ID:EVT-001", ... ] 모양이다. 사람이 읽기 편한 글로 하려면 for line in lines: file.write(line + "\n")로 바꾼다.
  • 앞으로 : 후속 조치 문장.
  • 리포트 5부분 : 사고 개요, 탐지 근거, 조치 내역, 현재 상태, 후속 조치.
  • containment_log.json이 기록 여러 건의 목록인지는 1·3파트에 확인해야 한다.
  • 파일 이름이나 모양이 다르면 5_상황별_고치기 문서를 본다.

main.py (오탐 처리까지 완료)

  • 하는 일 : 1~5번을 위에서 아래로 한 번 돌려서 이벤트를 끝까지 처리하고, 오탐 입력 파일에 적힌 이벤트는 오탐 처리까지 한다. 함수는 없고 다른 파일의 함수를 부르기만 한다.
  • 읽는 파일 : detections.json, vip_accounts.json, containment_log.json, false_positive_input.json (오탐으로 확인한 이벤트 목록. 없으면 오탐 처리는 건너뛴다)
  • 만드는 파일 : 티켓이 있는 이벤트마다 report_이벤트번호.json, 오탐 처리를 하면 false_positive_feedback.json
  • 단계 : 1 파일 읽기 → 2 빈 서랍장 4개 statuses, tickets, requests, events → 3 이벤트마다 run_playbook, 요청이 None이 아니면 make_ticket을 하고 요청과 이벤트를 requests, events에 보관 → 4 조치 결과로 apply_result, update_ticket → 5 티켓마다 make_report, save_report → 5-2 오탐 입력 파일의 이벤트마다 handle_false_positive (복구 요청 만들기 + 오탐 기록 저장)
  • 순서 주의 : 4단계가 5단계보다 위에 있어야 한다. 아래에 있으면 에러 없이 저장된 리포트에 조치 결과:결과 없음, 현재 상태:조치중이 남는다.
  • 4단계의 result는 EVT-001 하나만 있는 가짜 값이다. 5-2단계도 이 값을 쓰므로 오탐 입력 파일에 다른 이벤트 번호를 적으면 맞지 않는 값이 들어간다. 1·3파트가 돌려준 진짜 결과로 바꾼다. 여러 건이면 5_상황별_고치기 문서 9장의 반복문을 쓴다.
  • 아직 없는 것 : 알림 요청(make_alert_request) 줄. 누가 알림을 부를지는 팀이 정해야 한다.
  • 5-2단계가 만든 복구 요청은 지금 화면에 찍기만 한다. 1·3파트에 넘기는 줄은 아직 없다. 오탐 입력 파일을 누가 만들지도 팀이 정해야 한다. (15장)
  • 코드는 4_코드모음 문서와 main.py 파일에 있다. 줄마다 값의 출처를 주석에 적었다.

9. main.py에 합치기▲ 맨 위

main.py가 합치는 순서는 이렇다. (아래는 줄이고 쓴 것이고, 실제 줄은 main.py에 있다.)

  • json 파일을 읽는다 (detections.json, vip_accounts.json, containment_log.json). 빈 서랍장 statuses, tickets, requests, events를 만든다.
  • 이벤트를 하나씩 꺼낸다.
  • request = run_playbook(event, vip_data, statuses)
  • request가 None이 아니면 ticket = make_ticket(event, request, statuses[event["event_id"]])
  • 1·3파트가 조치를 실행하고 result를 돌려주면 apply_result(statuses, result)와 ticket = update_ticket(ticket, result)
  • 알림이 필요하면 make_alert_request(event, level, message)
  • 오탐이면 handle_false_positive(event, request, result, reason, confirmed_by)

main.py 4단계의 조치 결과는 가짜로 만든 값이다. 실제로는 1·3파트가 돌려준 값을 넣는다.

이 순서 뒤에 main.py는 두 가지를 더 한다. 이벤트를 다 돌린 뒤 티켓마다 lines = make_report(tickets[event_id], logs), save_report(lines, "report_" + event_id + ".json")를 한다. 그다음 5-2단계로 false_positive_input.json을 읽어 이벤트마다 handle_false_positive(events[event_id], requests[event_id], result, item["reason"], item["confirmed_by"])를 부른다.

합칠 때 순서 주의 : apply_result, update_ticket은 make_report, save_report보다 먼저 부른다. 반대로 하면 에러 없이 저장된 리포트에 결과가 빠진다. main.py 맨 아래 확인 코드의 저장 내용 같은가: True로 확인한다.

10. 다른 파트와 연결▲ 맨 위

  • 2파트 → 나 : detections.json의 이벤트. 칸 11개가 모두 있어야 한다.
  • 나 → 1·3파트 : 조치 요청 6칸 (run_playbook의 결과).
  • 1·3파트 → 나 : 조치 결과 7칸. 이것으로 apply_result, update_ticket을 부른다.
  • 1·3파트 → 나 : containment_log.json. report.py가 읽는다.
  • 나 → 알림 : 알림 요청 4칸. 누가 보내는지는 팀이 정해야 한다.

바꿀 수 있는 곳

  • 칸 이름이 다르면 해당 파일에서 event["이름"]을 그 이름으로 바꾼다.
  • 조치 이름이 다르면 playbook.py의 choose_action과 false_positive.py의 choose_restore_action을 같이 고친다.

11. 다른 사람 코드 확인법▲ 맨 위

다른 파트 코드를 받았을 때 다음 순서로 본다.

  • 1 파일을 열기 전에 칸 이름을 공통로그 카드와 대조한다. 철자 한 글자 차이(imapct_scope)가 KeyError가 된다.
  • 2 import한 파일이 같은 폴더에 있는지 본다.
  • 3 파일 읽기 줄이 if __name__ == "__main__": 밖에 있는지 본다. 밖에 있으면 import 할 때 실행된다.
  • 4 맨 위에 print가 있는지 본다. 있으면 import 할 때 화면에 나온다.
  • 5 def 괄호 순서와 부르는 쪽 값 순서가 같은지 본다.
  • 6 return이 있는지, None을 돌려줄 수 있는지 본다. None을 돌려주면 받는 쪽에서 [ ]를 쓸 때 TypeError가 난다.
  • 7 글자 값이 팀 표준과 같은지 본다 (즉시 자동조치의 띄어쓰기 등).
  • 8 직접 실행해 본다.

합칠 때 바꿔야 할 곳

  • 상대 함수가 None을 돌려주면 내 쪽에서 if x is not None:을 넣는다.
  • 상대 칸 이름이 다르면 event["…"]를 그 이름으로 맞춘다.
  • 상태 글자를 상대가 다르게 쓰면 first_status와 apply_result 글자를 맞춘다.

12. 보류 같은 새 등급이 생기면▲ 맨 위

팀 표준 등급은 3개라 보류는 없다. 4번째 등급이 생기면 아래 3곳을 고친다.

  • classifier.py의 event_check : 새 등급을 돌려줄 조건을 더한다.
  • playbook.py의 first_status : 새 등급 글자를 보고 상태를 정한다.
  • playbook.py의 run_playbook : 새 등급일 때 요청을 만들지 정한다.

ticket.py는 바꾸지 않아도 된다.

이 3곳을 안 고치면 새 등급은 first_status의 마지막 else로 가서 신규가 된다.

13. 문제가 생기면▲ 맨 위

  • TypeError: 'set' object is not subscriptable : 서랍장 만드는 줄에서 "이름": 값 모양이 깨졌다. 점(...)이나 콜론 빠짐을 본다.
  • TypeError: 'NoneType' object is not subscriptable : None을 [ ]로 열었다. 보통 run_playbook이 None을 돌려준 이벤트로 make_ticket을 불렀다.
  • FileNotFoundError : 실행하는 폴더에 json이 없다. 또는 읽는 줄이 __main__ 밖에 있다.
  • KeyError : 서랍장에 없는 이름표. 철자를 본다.
  • UnicodeDecodeError 또는 글자가 깨짐 : 한글 json을 encoding 없이 읽었다. encoding="utf-8"을 더한다.
  • ImportError : 파일 이름이나 함수 이름이 다르다. 같은 폴더인지 본다.

14. 알아 둘 점▲ 맨 위

이 문서를 믿기 전에 알아 둘 것

  • Claude가 직접 실행해 확인한 곳은 Claude의 실행 환경이다. 대영의 컴퓨터에서 실행한 결과는 대영이 보여 준 화면 기준이다. (report.py 줄 수 19, 19, 16과 저장 True, main.py 이벤트 1건 기준 확인 출력)
  • 1파트·3파트의 실제 코드를 못 봤다. 공통로그 카드 기준으로만 맞췄다.
  • 강의 평가 기준을 못 봤다.
  • ticket.py의 update_ticket은 조치가 성공하면 상태를 완료로 바꾼다. 강의에서는 조치 성공만으로 티켓을 자동 종료하지 말라고 했다. 팀이 정해야 한다.
  • 알림 요청을 누가 부를지는 정해지지 않았다.
  • classifier.py와 false_positive.py의 open에 encoding="utf-8"을 더한 것은 이 문서의 코드에만 적용했다. 대영의 컴퓨터 파일에 적용됐는지는 확인하지 못했다.
  • 대영의 make_ticket에 rule, evidence가 들어 있는지 확인하지 못했다. 이 문서의 코드에는 들어 있다.
  • to의 글자가 보안 팀장(띄어쓰기)인지 보안팀장인지 대영 파일과 이 문서 코드가 다를 수 있다.
  • report.py는 후속 조치가 아직 없다. 테스트(줄 수 19, 19, 16, 저장 True)는 Claude 환경에서만 실행했다.
  • 이 문서의 5번 문서(5_상황별_고치기)는 파일 이름, 모양, 칸 이름, 글자가 다를 때 어디를 어떻게 고치는지 적었다.
  • main.py는 이번 작업에서 대영 컴퓨터의 실제 파일을 읽지 못했다(연결이 안 됐다). 이 문서의 main.py는 대화에 나온 코드 기준이다. 대영 파일과 한 줄씩 다를 수 있다.
  • 대영 컴퓨터의 detections.json은 이벤트 1건(사용자 글자 em3, 점수 80)이고, 프로젝트에 올린 샘플은 7건(사용자 emp3 ~ emp8, admin)이다. 어느 쪽이 팀 최신인지 확인하지 못했다.
  • main.py의 조치 결과(4단계)는 가짜 값이다. 알림 요청 줄은 아직 없다. 5-2단계의 복구 요청은 지금 화면에 찍기만 하고 1·3파트에 넘기지 않는다. 5-2단계의 result는 EVT-001 하나뿐이라서 다른 이벤트 번호를 오탐 입력 파일에 쓰면 맞지 않는 값이 들어간다. 오탐 입력 파일을 누가 어떻게 만들지는 팀이 정해야 한다.

15. 팀에 정해 달라고 묻는 것 (아직 안 정해진 것 전부)▲ 맨 위

4파트 코드와 문서에서 "팀이 정해야 한다", "확인 필요", "가짜 값", "임시"라고 적어 둔 것을 한곳에 모았다. 코드 안 주석에서 찾은 것과 문서에서 찾은 것이다. 항목마다 4가지를 적었다.

  • 어디에 있나 (파일, 함수)
  • 지금 코드는 어떻게 되어 있나
  • 누구에게 무엇을 물어볼까
  • 정해지면 어디를 고치나 (5_상황별_고치기 문서의 칸)

합치기 전에 꼭 물어볼 것은 아래 6개이다. 이 6개가 정해져야 main.py가 1·3파트와 이어진다.

  • 알림 요청을 누가 부르나 ↗
  • 오탐 입력 파일은 누가 어떻게 만드나 ↗
  • 복구 요청을 1·3파트에 어떻게 넘기나 ↗
  • 1·3파트가 조치 결과를 어떤 모양으로 돌려주나 ↗
  • 조치 이력 파일 containment_log.json은 목록인가 ↗
  • detections.json은 어느 것이 최신인가 ↗

그 밖에 4파트가 임시로 정해 둔 것, 팀 표준과 다른 것은 아래에 있다. 모든 항목은 정해질 때까지 지금 코드가 그대로 돈다.
